# ☕ Java 8 → 11 → 17 → 21 → 25: The Architect's Interview Cheatsheet

*Read it once top to bottom, then use it as a lookup. Each version has a kid-simple analogy, the "why", a production scenario, and best and worst cases.*

---

## 0. The 60-Second Big Picture

Imagine Java as a **kitchen** that gets renovated every few years.

| Version | Year | Theme | One-line memory hook |
|---|---|---|---|
| **8** | 2014 | Functional revolution | "Java learned to pass *actions* around" (lambdas, streams) |
| **11** | 2018 | Grown-up cleanup | "Remove junk, add HTTP client, finish the 9/10 work" |
| **17** | 2021 | Modern data modelling | "Records, sealed types, text blocks, switch expressions" |
| **21** | 2023 | Concurrency revolution | "Virtual threads, pattern matching grows up" |
| **25** | 2025 | Polish and performance | "Scoped values, compact headers, simpler beginner Java, faster startup" |

**LTS** (Long-Term Support) means vendors give patches for years. 8, 11, 17, 21 and 25 are all LTS. Since 21, a new LTS arrives **every 2 years** (the next is 29).

**Architect's rule of thumb:** in production, you choose an LTS. Between LTS versions, features arrive as **preview** (try, don't ship) or **incubator** (experimental API) and then become **final**. Interviewers love asking "what's the difference?"

# 🟠 PART 1: JAVA 8 (March 2014)

> **Kid version:** Before Java 8, if you wanted a robot to do a chore, you had to build a whole robot. Now you just hand it a sticky note saying what to do.

### 1.1 Lambda Expressions

A lambda is a short anonymous function: `(inputs) -> result`.

```java
// Before
Collections.sort(people, new Comparator<Person>() {
    public int compare(Person a, Person b) { return a.getAge() - b.getAge(); }
});
// After
people.sort(Comparator.comparingInt(Person::getAge));
```

- **Why:** Less boilerplate. It enables the functional style and made streams possible.
- **How it works:** The compiler uses `invokedynamic`, not a hidden inner class per lambda. This is a favourite deep question.
- **Rule:** Captured local variables must be **effectively final**.
- **Best case:** Small, readable behaviour such as callbacks, comparators and predicates.
- **Worst case:** Multi-line lambdas with side effects, which are unreadable and hard to debug. Extract a method instead.

### 1.2 Functional Interfaces

An interface with **exactly one abstract method** (annotate with `@FunctionalInterface`).

| Interface | Shape | Think |
|---|---|---|
| `Predicate<T>` | T → boolean | "Is it OK?" |
| `Function<T,R>` | T → R | "Convert it" |
| `Consumer<T>` | T → void | "Do something with it" |
| `Supplier<T>` | () → T | "Give me one" |
| `UnaryOperator<T>` / `BinaryOperator<T>` | T→T / (T,T)→T | "Same type in and out" |

- **Production tip:** Use the primitive versions (`IntPredicate`, `ToLongFunction`, and so on) in hot paths to avoid **boxing**.

### 1.3 Method References

Shorthand for a lambda that only calls one method: `String::toUpperCase`, `this::validate`, `User::new`.

### 1.4 Streams API

> **Kid version:** A conveyor belt. Items go in, pass through stations (filter, map), and come out as a result.

```java
Map<String, Double> avgSalaryByDept = employees.stream()
    .filter(Employee::isActive)
    .collect(Collectors.groupingBy(Employee::getDept,
             Collectors.averagingDouble(Employee::getSalary)));
```

- **Intermediate ops** (`filter`, `map`, `sorted`) are lazy. **Terminal ops** (`collect`, `forEach`, `count`) trigger the work.
- A stream is **single-use**. Reusing it throws `IllegalStateException`.
- **Parallel streams:** `parallelStream()` uses the **common ForkJoinPool**, which is shared JVM-wide.
- **Best case:** CPU-bound work on large in-memory collections, and readable data transformation.
- **Worst case (production incident):**
  - A parallel stream doing **blocking I/O** (DB or HTTP calls) starves the common pool, and unrelated parts of the app freeze.
  - Small collections get *slower* in parallel.
  - Side effects inside `map` or `forEach` break under parallelism.
- **Rule:** In services, avoid `parallelStream()` unless you've benchmarked it.

### 1.5 Optional

> **Kid version:** A lunchbox that may or may not contain a sandwich. You must check before eating.

```java
String city = Optional.ofNullable(user)
    .map(User::getAddress).map(Address::getCity).orElse("Unknown");
```

- **`orElse` vs `orElseGet`:** `orElse(x)` always evaluates `x`, even if the value is present. `orElseGet(() -> x)` is lazy. Use `orElseGet` when the default is expensive (a DB call).
- **Don't** use `Optional` for fields, method parameters or collections. It's meant for **return types**.
- **Worst case:** `optional.get()` without checking, which is just a NullPointerException in disguise.

### 1.6 Default and Static Methods in Interfaces

- **Why:** Evolve interfaces without breaking existing implementers. This is how `List.sort()` and `Collection.stream()` were added.
- **Diamond conflict rules:** (1) a class method wins over an interface method, (2) the more specific interface wins, (3) otherwise you must override and call `A.super.hello()`.
- **Worst case:** Turning interfaces into "abstract classes with state-like logic". Keep defaults small.

### 1.7 New Date/Time API (`java.time`)

`LocalDate`, `LocalDateTime`, `ZonedDateTime`, `Instant`, `Duration`, `Period`, `DateTimeFormatter`.

- **Why:** Old `Date` and `SimpleDateFormat` were mutable and **not thread-safe**. The new classes are immutable and thread-safe.
- **Production rule:** Store and transmit time as **`Instant` (UTC)**. Convert to `ZonedDateTime` only at the display edge.
- **Worst case:** Using `LocalDateTime` for events across time zones. It has no zone, so it's ambiguous.

### 1.8 CompletableFuture

> **Kid version:** An order-ticket at a restaurant. You get a ticket now, do other things, and the food arrives later.

```java
CompletableFuture<Order> f = CompletableFuture
    .supplyAsync(() -> fetchUser(id), ioPool)
    .thenCompose(u -> CompletableFuture.supplyAsync(() -> fetchOrder(u), ioPool))
    .exceptionally(ex -> fallbackOrder());
```

| Method | Meaning |
|---|---|
| `thenApply` | transform the result (map) |
| `thenCompose` | chain another async step (flatMap) |
| `thenCombine` | join two independent futures |
| `allOf` / `anyOf` | wait for all or the first |
| `exceptionally` / `handle` | error handling |

- **Production rule:** **Always pass your own executor**. The default is the common ForkJoinPool, which is shared with parallel streams.
- **Worst case:** No timeouts (Java 9 added `orTimeout`) and swallowed exceptions.

### 1.8b Other Java 8 Items (rapid-fire)

| Feature | Why it matters |
|---|---|
| `Map.computeIfAbsent / merge / getOrDefault` | Cleaner counters and caches (`map.merge(w, 1, Integer::sum)`) |
| **HashMap treeification** | A bucket with ≥8 collisions becomes a red-black tree (O(n)→O(log n)), which protects against hash-flooding |
| **ConcurrentHashMap rewrite** | No more segments. Uses CAS plus locking only the bucket head |
| **PermGen → Metaspace** | Class metadata moved to native memory. Tune with `-XX:MaxMetaspaceSize`. Classloader leaks now eat native memory |
| `StringJoiner`, `String.join` | Simple joining |
| `Base64` | Built-in encoder and decoder |
| `LongAdder`, `StampedLock` | Higher-throughput counters and locks |
| `Arrays.parallelSort` | Parallel sorting |
| Repeating and type annotations | Framework-level use |
| Nashorn (JS engine) | Deprecated in 11, removed in 15 |

**Java 8 interview one-liner:** *"Java 8 turned Java from purely object-oriented into object-oriented plus functional, which is lambdas, streams, Optional, CompletableFuture and java.time."*

# 🔵 PART 1.5: The Bridge: Java 9 and 10 (you inherit these in 11)

Interviewers say "Java 8 to 11" and mean 9, 10 and 11 together.

| Feature | Note |
|---|---|
| **Modules (JPMS)** | `module-info.java` gives strong encapsulation. Few app teams adopt it fully. It matters because it led to the JDK internals lockdown |
| **`List.of / Set.of / Map.of`** | **Immutable**, null-hostile, and `Set.of` throws on duplicates |
| **`var` (Java 10)** | Local variable type inference, compile-time only. It is *not* dynamic typing |
| Private interface methods | Share code between default methods |
| `Optional.ifPresentOrElse / or / stream` | Nicer Optional use |
| `Stream.takeWhile / dropWhile / iterate(3-arg)` | Short-circuit slicing |
| `Collectors.toUnmodifiableList`, `List.copyOf` | Immutability helpers |
| **G1 becomes default GC (9)** | Replaced Parallel GC as the default |
| **Container awareness (10)** | The JVM reads cgroup CPU and memory limits, so Docker and K8s sizing finally works |
| Compact Strings (9) | `String` uses byte[] (Latin-1 or UTF-16), so less heap |
| jshell | REPL for experiments |

> **`var` rule:** use it when the type is obvious from the right side (`var users = new ArrayList<User>()`). Avoid it when it hides meaning (`var x = process();`).

# 🟢 PART 2: JAVA 11 (September 2018, LTS)

> **Kid version:** Spring cleaning. Throw out the old furniture (Java EE, CORBA), add a modern doorbell (HTTP client), and label everything better (String methods).

### 2.1 Standard HTTP Client (`java.net.http`)

```java
var client = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();
var req = HttpRequest.newBuilder(URI.create("https://api.example.com/x"))
                     .timeout(Duration.ofSeconds(3)).build();
HttpResponse<String> res = client.send(req, BodyHandlers.ofString());
// async: client.sendAsync(req, BodyHandlers.ofString())
```

- **Why:** It replaces the clunky `HttpURLConnection` and supports HTTP/2, async calls and WebSocket.
- **Production gotcha:** **No request timeout by default.** Always set connect and request timeouts, or one slow upstream hangs your threads.
- **Best case:** Lightweight service-to-service calls without extra dependencies.
- **Worst case:** Ignoring connection reuse (create ONE client and share it), and a missing timeout.

### 2.2 New String Methods

| Method | Does |
|---|---|
| `isBlank()` | true for empty or whitespace-only |
| `strip()` / `stripLeading()` / `stripTrailing()` | Unicode-aware (better than `trim()`) |
| `lines()` | `Stream<String>` of lines |
| `repeat(n)` | `"ab".repeat(3)` → `ababab` |

### 2.3 Files and Misc API Additions

- `Files.readString(path)` / `Files.writeString(path, text)`. Great for small files, but **don't** use them on a 5 GB log.
- `Path.of(...)`
- `Predicate.not(String::isBlank)` for clean filter negation
- `Optional.isEmpty()`
- `Collection.toArray(String[]::new)`

### 2.4 `var` in Lambda Parameters

`(var x, var y) -> x + y`. Its only real benefit is adding annotations (`@NonNull var x`).

### 2.5 Single-File Source Launch

`java Hello.java` compiles and runs in one step. Good for scripts and demos, not for production.

### 2.6 JVM and Platform Changes (architect-level)

| Change | Impact |
|---|---|
| **Java EE and CORBA modules removed** | `javax.xml.bind` (JAXB), `javax.activation` and the like are gone. **Add the dependencies explicitly.** This is the #1 migration break from 8 |
| **JavaFX and Nashorn** | JavaFX was removed from the JDK. Nashorn was deprecated |
| **Flight Recorder (JFR) open-sourced** | Free, low-overhead production profiling |
| **TLS 1.3** | Faster and more secure handshakes |
| **ZGC (experimental)** | The first low-latency GC. It became production-ready in 15 |
| **Epsilon GC** | A "do-nothing" GC. Useful for benchmarking and ultra-short-lived jobs |
| **Nest-based access control** | Inner classes access private members without hidden bridge methods |
| **Oracle licensing change** | Oracle JDK became paid for commercial production. Use OpenJDK builds (Temurin, Corretto, Zulu, and so on) |

**Migration pain from 8 to 11:**
1. Missing `javax.*` modules. Add the Jakarta or JAXB libraries.
2. Old libraries doing reflection on JDK internals trigger "illegal reflective access" warnings.
3. Removed or changed JVM flags.
4. **GC logging flags changed** to unified logging (`-Xlog:gc*` replaces `-XX:+PrintGCDetails`).

**Java 11 interview one-liner:** *"Java 11 is the first 'modern baseline' LTS: HTTP client, container awareness, JFR free, and the end of Java EE inside the JDK."*

# 🟣 PART 3: JAVA 17 (September 2021, LTS)

Java 17 bundles everything from 12 to 17, so it's a big jump from 11.

> **Kid version:** Lego with proper instruction sheets. You can now describe *shapes of data* clearly and the compiler checks your work.

### 3.1 Records (final in 16)

```java
public record Point(int x, int y) {
    public Point {                       // compact constructor = validation
        if (x < 0) throw new IllegalArgumentException("x<0");
    }
}
```

- The compiler generates the constructor, getters (`p.x()`), `equals`, `hashCode` and `toString`.
- **Shallowly immutable.** If a field is a mutable `List`, the list can still change. Use `List.copyOf` in the compact constructor.
- Records are `final`, **cannot extend a class**, but **can implement interfaces**.
- **Where:** DTOs, API responses, value objects, Kafka events, map keys, query projections.
- **Where NOT:** **JPA/Hibernate entities.** Entities need a no-arg constructor, mutability and proxies. A record's immutability fights that.
- **Best case:** It replaces about 50 lines of boilerplate, and Jackson (2.12+) supports it.
- **Worst case:** Using records for objects with identity or lifecycle (an `Order` that changes status).

### 3.2 Sealed Classes and Interfaces (final in 17)

> **Kid version:** A club with a fixed member list. Only the people on the list can join.

```java
public sealed interface Payment permits Card, Upi, NetBanking {}
public record Card(String no) implements Payment {}
public record Upi(String id) implements Payment {}
public final class NetBanking implements Payment {}
```

- Each permitted subtype must be `final`, `sealed` or `non-sealed`.
- **Why:** You get a **closed hierarchy**, and in Java 21 the compiler can check that a `switch` handles *every* case.
- **Production scenario:** A payment-state or command model. Add a new payment type and every `switch` that forgot it **fails to compile**. This is a bug caught at build time, not at 2 AM.
- **Worst case:** Sealing types that third parties legitimately need to extend (library APIs).

### 3.3 Switch Expressions (final in 14)

```java
String label = switch (day) {
    case MON, TUE, WED, THU, FRI -> "Weekday";
    case SAT, SUN -> "Weekend";
};   // returns a value, no fall-through, no 'break' bugs
```

Use `yield` inside block bodies. With enums, the compiler checks that all cases are covered.

### 3.4 Text Blocks (final in 15)

```java
String json = """
    {
      "name": "Shubham",
      "role": "Architect"
    }
    """;
```

Great for SQL, JSON and HTML in code. Indentation is trimmed automatically. **Worst case:** inlining huge SQL instead of externalizing it.

### 3.5 Pattern Matching for `instanceof` (final in 16)

```java
if (obj instanceof String s && s.length() > 5) { System.out.println(s.toUpperCase()); }
```

No more manual cast after the type check.

### 3.6 Helpful NullPointerExceptions (14/15+)

The message now says exactly what was null: `Cannot invoke "String.length()" because "user.getName()" is null`. This helps production debugging a lot.

### 3.7 Other Java 12–17 Items

| Feature | Notes |
|---|---|
| `Stream.toList()` (16) | **Unmodifiable**, allows nulls. Not the same as `Collectors.toList()` |
| `Stream.mapMulti` (16) | Optimized one-to-many mapping |
| `Collectors.teeing` (12) | Two collectors, one pass |
| `HexFormat` (17) | Hex encoding and decoding |
| **Strong encapsulation of JDK internals (JEP 403)** | `--illegal-access` is gone. Old libraries break unless you pass `--add-opens`. **Migration blocker #1 from 11 to 17** |
| **ZGC and Shenandoah production-ready** | Low-pause collectors |
| **New RandomGenerator API** | Pluggable PRNGs (`RandomGenerator.of("L64X128MixRandom")`) |
| **Security Manager deprecated for removal** | Moving away from sandboxing |
| `jpackage` (16) | Native installers |
| Unix-domain sockets (16) | Fast local IPC |
| Elastic Metaspace (16) | Better class-metadata memory return |
| Vector API, Foreign API | Incubating at this stage |
| macOS/AArch64 port | Apple Silicon support |

### 3.8 Why 17 Matters for Spring Folks

**Spring Framework 6 and Spring Boot 3 require Java 17+** and also moved from `javax.*` to `jakarta.*`. So the real-world migration is "Java 8 → 17 + Boot 2 → 3 + javax → jakarta", usually done in steps.

**Java 17 interview one-liner:** *"Java 17 is where data-oriented Java starts: records, sealed types, pattern matching, text blocks. It's the minimum for Spring Boot 3."*

# 🔴 PART 4: JAVA 21 (September 2023, LTS)

> **Kid version:** Before, every waiter (thread) was a full-time employee who stood still while waiting for the kitchen. Now you have millions of tiny helper-waiters who step aside while waiting and are reused instantly.

### 4.1 Virtual Threads (JEP 444, the headline feature)

```java
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        exec.submit(() -> callSlowService());   // each task gets its own cheap thread
    }
}
// or: Thread.ofVirtual().name("worker").start(task);
```

**How it works (be able to draw this):**
- A **virtual thread** is a lightweight thread managed by the JVM, not the OS.
- It runs *mounted* on a small pool of **carrier threads** (platform threads, by default as many as CPU cores).
- When it hits **blocking I/O** (sleep, socket, lock via `java.util.concurrent`), it **unmounts**. The carrier is freed for others, and the virtual thread's stack is kept on the heap.
- When the I/O completes, it is mounted again.

**When to use:** I/O-bound, high-concurrency, request-per-thread apps: REST backends, fan-out to many microservices, DB-heavy services. You get scalability **without rewriting to reactive style**.

**Spring Boot 3.2+:** set `spring.threads.virtual.enabled=true`.

**Do NOT:**
- **Pool them.** Create one per task. They are cheap.
- Use them for **CPU-bound** work. There's no benefit, since you're limited by cores.
- Use `ThreadLocal` for heavy objects. A million virtual threads means a million copies.

**Production pitfalls (interview gold):**

| Pitfall | Explanation and fix |
|---|---|
| **Pinning** | A virtual thread stuck to its carrier while blocked. In 21–23 this happened inside **`synchronized`** blocks and native/foreign frames. **Java 24 (JEP 491) fixed `synchronized` pinning**. Before that, use `ReentrantLock`. Detect with `-Djdk.tracePinnedThreads` or the JFR event `jdk.VirtualThreadPinned` |
| **Downstream bottleneck** | 100k virtual threads hitting a DB pool of 20 connections just queue up. **Limit concurrency with a `Semaphore`**, not by shrinking thread count |
| **Observability** | Thread dumps with millions of threads are huge. Use `jcmd <pid> Thread.dump_to_file -format=json` |
| **Wrong mental model** | Virtual threads give **throughput under waiting**, not faster single requests |

- **Best case:** A service waiting on 5 downstream calls per request, where thread-per-request now scales to tens of thousands of concurrent requests.
- **Worst case:** A CPU-heavy image-processing service, where nothing improves and you've added debugging complexity.

### 4.2 Pattern Matching for `switch` (final in 21)

```java
String describe(Object o) {
    return switch (o) {
        case null            -> "nothing";
        case Integer i when i > 100 -> "big number";
        case Integer i       -> "number " + i;
        case String s        -> "text " + s.length();
        default              -> "unknown";
    };
}
```

- Works on **types**, supports **guards** (`when`) and handles `null` directly.
- With **sealed types**, no `default` is needed. The compiler enforces exhaustiveness.

### 4.3 Record Patterns (final in 21)

```java
sealed interface Shape permits Circle, Rect {}
record Circle(double r) implements Shape {}
record Rect(double w, double h) implements Shape {}

double area(Shape s) {
    return switch (s) {
        case Circle(double r)       -> Math.PI * r * r;
        case Rect(double w, double h) -> w * h;
    };
}
```

> **Together this is "data-oriented programming":** records (data) + sealed (closed set) + pattern matching (behavior). It replaces the old Visitor pattern in many cases.

### 4.4 Sequenced Collections (JEP 431)

A long-missing "first and last" API.

```java
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
list.getFirst();  list.getLast();  list.reversed();  list.addFirst(0);
```

New interfaces: `SequencedCollection`, `SequencedSet`, `SequencedMap`. They are implemented by `List`, `Deque`, `LinkedHashSet/Map` and `SortedSet/Map`. **Worst case:** calling `getFirst()` on an empty collection throws `NoSuchElementException`.

### 4.5 Generational ZGC

`-XX:+UseZGC -XX:+ZGenerational` (opt-in in 21). It became the **default ZGC mode in 23**, and the non-generational mode was removed in 24.

- **Why:** Young objects die fast, so collecting them separately lowers CPU and memory overhead.
- **Best case:** Large heaps (tens or hundreds of GB) needing **sub-millisecond-class pauses**.
- **Worst case:** Using ZGC on tiny heaps and expecting miracles. G1 is fine there.

### 4.6 Smaller 21 Items

`StringBuilder.repeat`, `Math.clamp`, `String.indexOf(ch, from, to)`, emoji methods on `Character`, the Key Encapsulation Mechanism (KEM) API, and a **warning when agents are loaded dynamically** (a step toward integrity-by-default).

### 4.7 Features from 18–20 You Inherit

- **UTF-8 is the default charset (Java 18, JEP 400).** This is a migration gotcha for apps that relied on the OS default (Windows).
- `jwebserver` (a simple static file server), and the Javadoc `@snippet` tag.

### 4.8 In Preview in 21 (don't use in prod, but know the names)

- **String Templates:** previewed, then **removed**. Don't build on them.
- **Unnamed patterns and variables (`_`):** final in 22.
- **Scoped Values:** final in 25.
- **Structured Concurrency:** *still* preview in 25.

**Java 21 interview one-liner:** *"Java 21 made blocking cheap again. Virtual threads give reactive-level scalability with simple blocking code, and pattern matching completes the data-oriented toolkit."*

# ⚫ PART 5: JAVA 25 (September 2025, LTS)

> **Kid version:** The renovation is done, so now it's polishing: smaller furniture (memory), faster doors (startup), and easier rules for beginners (simple source files).

Java 25 includes everything from 22, 23, 24 and 25. Here's the architect-level view.

### 5.1 Final in 25

#### Scoped Values (JEP 506)

> **Kid version:** A badge you wear *only inside a room*. When you leave the room, the badge is gone. Everyone inside can read it, but no one can change it.

```java
static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, user).run(() -> handleRequest());
// anywhere deeper: CURRENT_USER.get()
```

| `ThreadLocal` | `ScopedValue` |
|---|---|
| Mutable, lives until removed | **Immutable**, tied to a scope |
| Easy to **leak** (thread pools) | Cleans up automatically |
| Costly with millions of threads | Built for virtual threads |
| Inherited by copying | Shared cheaply with child threads |

- **Where:** Request context (user, trace ID, tenant) across call layers.
- **Worst case:** Using it where you need *mutable* per-thread state. It's immutable by design.

#### Flexible Constructor Bodies (JEP 513)

You can run statements **before** `super(...)` or `this(...)`, as long as they don't use `this`.

```java
class Employee extends Person {
    Employee(String name, int age) {
        if (age < 18) throw new IllegalArgumentException("Too young");  // validate FIRST
        super(name, age);
    }
}
```

Before this, you needed awkward static helper methods to validate arguments.

#### Compact Source Files and Instance `main` (JEP 512)

```java
void main() { IO.println("Hello"); }
```

No `public static void main(String[] args)` ceremony and no class wrapper. Easier for beginners and scripts. It is not a production architecture feature, but a likely trivia question.

#### Module Import Declarations (JEP 511)

`import module java.base;` imports all public packages of a module at once. It is convenient for scripts and teaching, and teams may skip it in large codebases for clarity.

#### Compact Object Headers (JEP 519)

- Object headers shrink from **12 bytes to 8 bytes** (64-bit JVM). Enable with `-XX:+UseCompactObjectHeaders` (opt-in in 25).
- **Why it matters:** Apps with millions of small objects (caches, graphs, DTO-heavy services) use less heap and can see better cache locality. Reported gains are workload-dependent, so **benchmark your own service**.
- **Worst case:** Turning it on blindly in prod. Test first, since some tools rely on header layout.

#### Generational Shenandoah (JEP 521)

A production version of generational Shenandoah, a low-pause GC. It's an alternative to ZGC, popular in some distributions.

#### Others

| Feature | Notes |
|---|---|
| **Key Derivation Function API** | A standard way to derive keys (crypto) |
| **AOT cache improvements (Project Leyden)** | Faster startup and warm-up (see 5.3) |
| **JFR upgrades** | CPU-time profiling (experimental, Linux), method timing and tracing, safer sampling |
| **32-bit x86 port removed** | Cleanup |

### 5.2 Final in 22–24 (now yours in 25)

| Feature | What and why |
|---|---|
| **Unnamed variables and patterns `_` (22)** | `catch (Exception _)`, `case Point(var x, _)`. Say clearly "I don't use this" |
| **Foreign Function and Memory API (22)** | Call native C libraries and manage off-heap memory **safely**. It replaces JNI. Useful for native ML libs, drivers and high-performance I/O |
| **Multi-file source launch (22)** | `java App.java` with several source files |
| **Stream Gatherers (24)** | Custom intermediate stream operations: `stream.gather(Gatherers.windowFixed(3))`, `windowSliding`, `fold`, `scan`, `mapConcurrent` |
| **Class-File API (24)** | A standard API to read and write `.class` files (for tooling and framework authors) |
| **`synchronized` no longer pins virtual threads (24)** | Removes the biggest virtual-thread gotcha |
| **Security Manager permanently disabled (24)** | Don't rely on it |
| **Post-quantum crypto (24)** | ML-KEM and ML-DSA support |
| **Markdown in Javadoc (23)** | `///` comments |
| **ZGC is generational-only (24)** | Simpler tuning |

```java
// Gatherers example
Stream.of(1,2,3,4,5).gather(Gatherers.windowFixed(2)).toList();  // [[1,2],[3,4],[5]]
```

### 5.3 Startup and Warm-up (Project Leyden: AOT cache)

> **Kid version:** Instead of re-reading the whole recipe every time you cook, you keep pre-prepared ingredients.

- Java 24 added **ahead-of-time class loading and linking**. Java 25 adds easier AOT command-line ergonomics and **AOT method profiling**.
- **How:** Run a **training run** to record, produce a cache file, then run production with that cache.
- **Why:** Faster startup and quicker warm-up for microservices, serverless and autoscaling pods.
- **Worst case:** A stale cache after code or dependency changes. Rebuild it in CI.

### 5.4 Still Preview or Incubator in 25 (know the status)

| Feature | Status |
|---|---|
| **Structured Concurrency** | Preview (fifth round). It treats subtasks as one unit that cancels together |

# 🧭 PART 6: Architect Playbooks

### 6.1 Which Java Version Should We Run?

| Situation | Recommendation |
|---|---|
| Greenfield service | **25** if your frameworks and libraries support it. **21** is the safe, widely supported alternative |
| Spring Boot 3.x / Framework 6 | **17 minimum**, ideally 21 or 25 |
| Legacy monolith on 8 | Move to **17**, then **21 or 25**. Don't jump blindly |
| I/O-heavy, high concurrency | **21+** (virtual threads) |
| Large heap, strict latency | **21+** with generational ZGC |
| Tiny serverless or CLI | **25** with AOT cache, or native image |

### 6.2 The Safe Migration Recipe (8 → 17 → 21 → 25)

1. **Inventory.** Run `jdeps` and `jdeprscan` to find internal API use and deprecated APIs.
2. **Upgrade build tools and plugins** (Maven, Gradle, compiler, Surefire, Jacoco).
3. **Upgrade dependencies** (Lombok, Mockito, ByteBuddy, Jackson, Hibernate and others). Old versions break on newer JDKs.
4. **Fix removed modules** (JAXB, javax.activation), **flags** (CMS is removed, PermGen flags are ignored) and **logging flags** (`-Xlog`).
5. **Handle strong encapsulation.** Prefer library upgrades. Use `--add-opens` only as a temporary bridge.
6. **Check charset.** UTF-8 became the default in 18.
7. **Set container flags:** `-XX:MaxRAMPercentage=75` and check `-XX:ActiveProcessorCount` where needed.
8. **Run both JDKs in CI** (a matrix), then canary-deploy and compare GC, latency and memory.
9. **Adopt features gradually.** Don't rewrite everything on day one.

### 6.3 Which GC?

| GC | Pick when | Watch out |
|---|---|---|
| **G1** (default) | General-purpose services | Pauses under huge heaps |
| **ZGC (generational)** | Big heaps, tight latency (p99) | Slightly more CPU overhead |
| **Shenandoah** | Low pauses, available in many distributions | Check your JDK vendor |
| **Parallel** | Batch and throughput jobs | Longer pauses |
| **Serial** | Tiny containers (1 CPU, small RAM) | Not for servers with real load |

# ❓ PART 7: FAQ (Current Trends and Common Traps)

**Q1. Why not stay on Java 8?**
Because of security patches (many vendors have limited or paid support for 8), missing performance work (better GCs, container awareness, JIT improvements), and the modern framework baseline (Spring Boot 3 needs 17+). The business case is "lower risk, lower infrastructure cost, better hiring".

**Q2. Virtual threads vs reactive (WebFlux): which one?**
- Virtual threads: simple blocking code, easy debugging, and good stack traces. Best for most I/O-bound services.
- Reactive: still valuable for **streaming and back-pressure** use cases and for teams already invested in it.
- Rule: *new CRUD or I/O service on 21+, start with virtual threads. Keep reactive where you need streaming semantics.*

**Q3. Do virtual threads replace thread pools?**
For *task-per-request concurrency*, yes: don't pool virtual threads. You still need **concurrency limits** (semaphores or bulkheads) to protect downstream resources, and pools for CPU-bound work.

**Q4. What is pinning and how do you fix it?**
A virtual thread is stuck to its carrier while blocked. In 21–23 it happened with `synchronized` and native frames. Fix: use `ReentrantLock`, upgrade to **24+** (synchronized pinning fixed), and watch the `jdk.VirtualThreadPinned` JFR event.

**Q5. ScopedValue vs ThreadLocal?**
`ScopedValue` is immutable, scope-bound, automatically cleaned up and cheaper with huge thread counts. `ThreadLocal` is mutable and leak-prone. Use scoped values for request context in new code.

**Q6. Is Structured Concurrency production-ready?**
Not in 25 (fifth preview). The idea: treat related subtasks as one unit so failure or cancellation propagates cleanly. Prototype it, and don't depend on it for production.

**Q7. Records vs Lombok `@Value`? Can records be JPA entities?**
Records are language-level, with no annotation processor needed. They suit DTOs and projections. **Not for JPA entities**, which need mutability, a no-arg constructor and proxies.

**Q8. What is "data-oriented programming" in Java?**
Model your domain as immutable **records**, restrict variants with **sealed** types and process them with **pattern-matching switch**. It's often simpler than deep inheritance or the Visitor pattern.

**Q9. `Stream.toList()` vs `Collectors.toList()` vs `toUnmodifiableList()`?**
- `Stream.toList()`: unmodifiable, allows nulls
- `Collectors.toList()`: no guarantees (usually an `ArrayList`, mutable)
- `Collectors.toUnmodifiableList()`: unmodifiable, **rejects nulls**

**Q10. `List.of` vs `Arrays.asList` vs `Collections.unmodifiableList`?**
- `List.of`: truly immutable, no nulls
- `Arrays.asList`: fixed-size but elements are settable, and it's a view of the array
- `unmodifiableList`: a read-only **view**. The underlying list can still change

**Q11. GraalVM native image vs AOT cache vs CRaC?**
- **Native image:** fastest startup and low memory, but a closed-world assumption (reflection needs configuration), longer builds and different peak performance.
- **AOT cache (Leyden):** stays on the normal JVM, so it's compatible and simpler, with moderate startup gains.
- **CRaC:** checkpoint and restore a warmed JVM. Strong for fast scale-out, but it needs platform support.

**Q12. How does Java behave in Docker and Kubernetes?**
The JVM is container-aware since 10. Set `-XX:MaxRAMPercentage` (commonly 60–75%), leave room for metaspace, thread stacks and native memory, and set CPU limits thoughtfully. The JVM picks the GC and thread counts from the CPU limit. **Under 2 CPUs or about 1.8 GB, the JVM may choose Serial GC** unless you override.

**Q13. What does "preview" vs "incubator" vs "final" mean?**
- **Preview:** a language or VM feature that may still change. It needs `--enable-preview`.
- **Incubator:** an experimental *API* in an incubator module.
- **Final:** supported and stable.

**Q14. What's coming that I should name-drop?**
- **Valhalla** (value classes, flatter memory)
- **Leyden** (startup and warm-up)
- **Loom** (virtual threads, structured concurrency, scoped values)
- **Panama** (FFM and the Vector API)
- **Amber** (language ergonomics: records, patterns, simpler syntax)
- **Lilliput** (compact object headers)

**Q15. Java and AI: why should I care as an architect?**
Frameworks like Spring AI and LangChain4j make LLM integration straightforward. Virtual threads help fan-out calls to model APIs. The FFM API and Vector API help integrate native or numeric libraries. Java's strength is the **production system around** the model: reliability, observability and security.

**Q16. Oracle JDK or OpenJDK?**
Pick a maintained OpenJDK distribution (Temurin, Corretto, Zulu, Microsoft and others) and check each vendor's support policy. Understand the licence terms before choosing, since this is a compliance question.

**Q17. Biggest breaking changes when upgrading?**
8 → 11: removed Java EE modules, GC flag and logging changes. 11 → 17: strong encapsulation (`--add-opens`), removed CMS and other flags. 17 → 21: mainly dependency compatibility. Also 18+: **UTF-8 default**. Always rely on tests, and canary before full rollout.

**Q18. Parallel streams in production?**
Rarely. They share the common pool, are bad for blocking calls and are hard to reason about under load. Benchmark first, or use a dedicated `ForkJoinPool` or executors.

**Q19. `Optional.orElse` vs `orElseGet`?**
`orElse` always evaluates its argument and `orElseGet` is lazy. Use `orElseGet` for anything expensive or with side effects.

**Q20. `var`: good or bad?**
Good when the type is obvious. Bad when it hides meaning. It is compile-time inference and Java is still statically typed.
