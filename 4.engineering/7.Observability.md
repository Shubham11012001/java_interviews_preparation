# Monitoring and Observability: The Complete Guide for Technical Architects

A practical, interview-focused tutorial · Beginner-friendly explanations · Production architecture · Senior and Technical Architect perspective

Imagine you are responsible for a banking application used by millions of customers. One morning, customers start complaining:

* Login takes 10 seconds instead of 1 second.

* Money transfers sometimes fail.

* The application occasionally returns HTTP 500 errors.

* The database CPU is at 95%.

* Your team says, “Everything looks fine on our machines!”

As a Technical Architect, how do you find the problem without guessing?

You need Monitoring and Observability.

Monitoring helps you detect that something is wrong. Observability helps you investigate why it is wrong.

This guide will take you from the fundamentals to production architecture, distributed tracing, SRE practices, OpenTelemetry, alerting strategies, cloud-native monitoring, and the questions you are likely to face in senior-level interviews.

## 1. What are monitoring and observability?

### 1.1 Monitoring: Is something wrong?

Monitoring means continuously collecting and checking information about a system to determine whether it is healthy.

Think of a car dashboard.

Add to Favorites

The dashboard tells you:

* How fast the car is moving.

* How much fuel remains.

* Whether the engine is overheating.

* Whether a warning light is on.

It tells you that a problem exists, or may soon exist.

In software, monitoring answers questions such as:

* Is the application running?

* How many requests are failing?

* Is CPU usage too high?

* Is the database running out of connections?

* Is response time increasing?

* Is the application meeting its availability target?

Example: Your Spring Boot API has a 12% error rate, and an alert fires.

Monitoring detects the problem. It may not immediately tell you the exact root cause.

### 1.2 Observability: Why is something wrong?

Observability is the ability to understand a system's internal behavior by examining the data it produces.

Imagine that the car dashboard shows the engine is overheating. Observability is like a mechanic examining the temperature history, coolant flow, engine behavior, and fault codes to determine the cause.

In a distributed application, observability helps answer:

* Which service caused the request to fail?

* Which database query is slow?

* Why are requests slower only in one region?

* Why did latency increase after the latest deployment?

* Is a downstream service failing, or is our application itself the problem?

* Why is one customer experiencing errors while others are not?

Example: A payment API is slow. A distributed trace shows that the API takes 100 ms, but its call to the customer-profile service takes 4 seconds. The investigation can now focus on that dependency.

### 1.3 Monitoring vs. observability

| Monitoring                                   | Observability                                       |
| -------------------------------------------- | --------------------------------------------------- |
| Detects known failure conditions             | Helps investigate unknown failure conditions        |
| Often uses predefined metrics and thresholds | Correlates metrics, logs, traces, and context       |
| Answers “What is broken?”                    | Helps answer “Why is it broken?”                    |
| Uses dashboards and alerts                   | Uses queries, traces, logs, and investigative tools |
| Example: CPU is above 90%                    | Example: Which workload is causing CPU saturation?  |

These are not competing approaches. Monitoring is an important part of an observable system. You need both.

A monitoring system without good diagnostic data may tell you that production is failing but leave your engineers guessing why.

## 2. Why does observability matter to a Technical Architect?

Consider a typical modern application:

Customer / Mobile App / Web App

API Gateway / Load Balancer

Order Service

Payment Service

Customer Service

Databases · Cache · Message Broker · External APIs

Observability Platform

Conceptual architecture: telemetry is collected from every relevant layer and correlated in a central observability platform.

Suppose a customer submits an order, but the payment fails.

Without observability, the team might inspect five services manually.

With observability, the team can follow the request across the gateway, order service, payment service, database, and external payment provider.

As an architect, your responsibility is not merely to select a monitoring tool. It is to design a system in which failures can be detected, diagnosed, and resolved efficiently.

Your decisions influence:

* Availability and reliability.

* Mean time to detect and recover from incidents.

* Customer experience.

* Infrastructure and telemetry costs.

* Security and auditability.

* Capacity planning.

* Compliance requirements.

* Deployment safety.

* Operational complexity.

A senior interviewer often wants to know whether you can design observability into the architecture rather than add dashboards after a production incident.

### 3. Traces — Where did the request go, and where was the time spent?

A distributed trace follows a request across multiple services. Each operation is represented by a span.

Best for: microservices, latency analysis, dependency failures, and distributed transactions.

### Example: Investigating a slow payment

Imagine a payment request takes 5 seconds.

| Signal  | What you discover                                             |
| ------- | ------------------------------------------------------------- |
| Metrics | Payment API p95 latency increased from 300 ms to 5 seconds    |
| Logs    | External payment provider returned a timeout                  |
| Traces  | The provider call consumed 4.6 seconds of the total 5 seconds |

Together, these signals help the team distinguish a local application problem from a dependency problem.

### Are there more than three pillars?

Yes. The three pillars are a useful teaching model, not a strict limit on observability.

Modern platforms also use:

* Profiles: where a program spends CPU time or allocates memory.

* Events: deployments, configuration changes, autoscaling events, and incidents.

* Continuous profiling: ongoing collection of performance profiles.

* Synthetic monitoring: automated tests that simulate customer journeys.

* Real user monitoring (RUM): actual browser or mobile user experience.

* Business telemetry: orders completed, payments declined, and other domain outcomes.

A mature observability strategy combines technical signals with customer and business outcomes.

## 4. Metrics: The foundation of monitoring

A metric is a numerical measurement associated with time.

Examples:

* 800 requests per second.

* 75% CPU utilization.

* 250 ms response time.

* 20 failed payments per minute.

* 1,200 messages waiting in a queue.

Metrics are usually much cheaper to store and query at scale than detailed event logs, making them especially useful for long-term trends and alerting.

### 4.1 The four golden signals

The four golden signals are a foundational framework for monitoring user-facing services.

1. Latency

How long does a request take?

Example: p95 latency is 400 ms.

Watch successful and failed requests separately when their timings differ.

2. Traffic

How much demand is the service receiving?

Example: 5,000 requests per second.

For different systems, traffic might mean transactions, messages consumed, or active sessions.

3. Errors

How many operations fail?

Example: 2% of API requests return server errors.

Include application failures, timeouts, and other failures that matter to the user.

4. Saturation

How close is a resource to its useful capacity?

Example: connection pool is at 98% utilization, or a message backlog is growing.

Saturation can reveal an outage before customers begin seeing failures.

Architect's interview tip: If asked how you would monitor a microservice, start with latency, traffic, errors, and saturation. Then add business-specific and infrastructure-specific metrics.

### 4.2 RED and USE methods

Two more useful frameworks help you choose metrics.

| Framework | Stands for                      | Best used for                    |
| --------- | ------------------------------- | -------------------------------- |
| RED       | Rate, Errors, Duration          | Request-driven services and APIs |
| USE       | Utilization, Saturation, Errors | Infrastructure and resources     |

RED example — Spring Boot API

* Rate: requests per second.

* Errors: failed requests per second or error percentage.

* Duration: request latency distribution.

USE example — database server

* Utilization: CPU and disk utilization.

* Saturation: runnable tasks, I/O queues, connection waits.

* Errors: disk errors, connection failures, or resource-specific failures.

These methods complement each other. RED shows how the service behaves; USE helps investigate whether its resources are constrained.

### 4.3 Metric types

Prometheus commonly uses four metric types.

| Type      | Simple explanation                                                         | Example                       |
| --------- | -------------------------------------------------------------------------- | ----------------------------- |
| Counter   | Only increases, apart from resets                                          | Total HTTP requests           |
| Gauge     | Can increase or decrease                                                   | Current active connections    |
| Histogram | Counts observations in configurable buckets and tracks their sum and count | Request duration distribution |
| Summary   | Calculates configured quantiles and tracks observations                    | Request duration in a process |

A counter is suitable for total requests. To calculate requests per second, calculate its rate over a time window.

A gauge is suitable for current queue depth.

A histogram is especially useful when you need to estimate latency percentiles across many application instances. Histogram buckets must be designed appropriately for the desired accuracy and cost.

Common interview question: Can a counter decrease?

Not during normal operation. Its observed value can reset when the process restarts, which is why rate calculations must account for counter resets.

### 4.4 Average vs. percentiles

Suppose 100 customers use your API.

* 90 customers get a response in 100 ms.

* 10 customers wait 3 seconds.

The average response time is:

90(100)+10(3000)100=390 ms\frac{90(100)+10(3000)}{100}=390\text{ ms}10090(100)+10(3000)=390 ms

An average of 390 ms may look acceptable, but 10% of customers experience a 3-second delay.

Percentiles reveal this more clearly:

* p50: the median; half of observations are at or below this value.

* p90: 90% of observations are at or below this value.

* p95: 95% of observations are at or below this value.

* p99: 99% of observations are at or below this value.

Why not use averages alone? Averages hide tail latency. Percentiles are important for user-facing APIs, databases, and services with strict latency requirements.

One subtle point: do not simply average the p95 values from multiple servers and call that the global p95. Use mergeable distributions, such as appropriately configured histogram buckets, or aggregate raw observations in a system designed to calculate the correct percentile.

### 4.5 What should you measure in production?

| Layer            | Important metrics                                                 |
| ---------------- | ----------------------------------------------------------------- |
| API              | Request rate, latency percentiles, error rate, active requests    |
| JVM              | Heap usage, GC pauses, allocation rate, thread count              |
| Database         | Query latency, connection pool usage, lock waits, replication lag |
| Kafka / Pub/Sub  | Consumer lag, backlog, publish failures, processing latency       |
| Redis            | Hit ratio, latency, memory, evictions, connection count           |
| Kubernetes       | Pod restarts, CPU throttling, memory pressure, pending pods       |
| Load balancer    | Request count, backend errors, connection failures                |
| Business         | Orders completed, payment success rate, duplicate transactions    |
| Batch processing | Records processed, records rejected, throughput, job duration     |

Important: More metrics do not automatically mean better observability. Measure what helps answer a real operational or business question.

## 5. Logs: Understanding what happened

A log is a record of an event that occurred in a system.

For example, a payment service might record:

JSON

```
{
  "timestamp": "2026-10-12T10:30:00Z",
  "level": "ERROR",
  "service.name": "payment-service",
  "event": "payment_provider_timeout",
  "order_id": "ORD-12345",
  "trace_id": "abc123",
  "duration_ms": 3000
}
```

This is a simplified structured log. In production, use actual trace identifiers and follow a consistent schema.

### 5.1 Log levels

| Level | Purpose                                       | Example                       |
| ----- | --------------------------------------------- | ----------------------------- |
| TRACE | Very detailed diagnostic information          | Internal execution details    |
| DEBUG | Developer troubleshooting                     | Cache lookup decision         |
| INFO  | Important normal events                       | Batch job completed           |
| WARN  | Unexpected condition that may need attention  | Retry scheduled after timeout |
| ERROR | An operation failed                           | Database write failed         |
| FATAL | Severe process-level failure, where supported | Application cannot initialize |

Java logging frameworks differ in whether they expose a FATAL level. Do not assume every framework supports every level.

### 5.2 What makes a good production log?

A good log should be:

* Structured, preferably JSON for machine processing.

* Timestamped with a consistent time standard.

* Associated with service name, version, environment, and relevant operation.

* Correlated with a trace or request ID when applicable.

* Meaningful enough to help diagnose the failure.

* Free from secrets and unnecessary personal data.

Bad log:

```
Something went wrong!!!
```

Better log:

```
event=database_query_failed
service=order-service
operation=load_order
error_type=QueryTimeout
trace_id=abc123
```

The second log gives the engineer a starting point.

### 5.3 Why structured logging matters

Imagine searching through ten million lines of free-form text to find payment failures.

With structured logs, you can filter by:

* Service.

* Error type.

* Time range.

* Environment.

* Trace ID.

* Deployment version.

This makes automated analysis and dashboards easier.

### 5.4 What is a correlation ID?

A correlation ID is an identifier used to connect related operations or log records.

For example:

```
API Gateway       correlation_id=REQ-100
Order Service     correlation_id=REQ-100
Payment Service   correlation_id=REQ-100
```

You can follow one request across multiple components.

A correlation ID and a trace ID are related concepts, but they are not identical:

* A correlation ID is a general-purpose identifier for related work.

* A trace ID identifies a distributed trace.

* A span ID identifies one operation within that trace.

In a modern distributed system, propagate standard trace context and include trace identifiers in logs where possible.

### 5.5 What should never be logged?

Never casually log:

* Passwords.

* Access tokens and API secrets.

* Private keys.

* Full payment-card details.

* Unnecessary sensitive personal information.

* Full request bodies containing confidential data.

For banking and financial systems, masking, access control, retention policies, encryption, and audit requirements are essential.

Architect's rule: Logs must help diagnose a system without becoming a new security vulnerability.

## 6. Distributed tracing: Following a request across microservices

Distributed tracing is one of the most important concepts for a Technical Architect working with microservices.

### 6.1 Why do we need it?

Consider this flow:

```
Customer
   |
   v
API Gateway                 20 ms
   |
   v
Order Service              100 ms
   |
   +----> Customer Service  50 ms
   |
   +----> Payment Service  2500 ms
   |             |
   |             v
   |        External Bank  2300 ms
   |
   v
Order Database              80 ms
```

The entire request takes approximately 2.6 seconds if the operations run sequentially and the timings are additive as shown.

The order service may be healthy, but the payment provider is slow.

A normal application log may show a timeout. A distributed trace shows the exact location and duration of each operation.

### 6.2 Trace, span, parent, and child

* Trace: The complete journey of a request.

* Span: One timed operation within that journey.

* Parent span: An operation that initiated another operation.

* Child span: An operation created by its parent.

* Trace context: Information propagated across service boundaries to link operations.

Example:

```
Trace: Create Order
|
+-- API Gateway
|
+-- Order Service
|   |
|   +-- Validate Request
|   |
|   +-- Customer Service Call
|   |
|   +-- Payment Service Call
|   |   |
|   |   +-- HTTP Call to Bank
|   |
|   +-- Database Insert
|
+-- Response
```

A trace is not necessarily a single thread. It may include operations executed by different services, threads, machines, or asynchronous consumers.

### 6.3 What is trace context propagation?

When the order service calls the payment service, it must propagate trace context so the payment service can continue the same trace.

OpenTelemetry commonly supports the W3C Trace Context standard, including the `traceparent` header for HTTP requests.

For asynchronous systems, trace context may be carried in message metadata. Propagation must be configured for the messaging technology and instrumentation.

Without propagation, you may see several disconnected traces instead of one connected request journey.

### 6.4 How does distributed tracing help with asynchronous systems?

Consider:

```
Order API
   |
   v
Publish OrderCreated
   |
   v
Message Broker
   |
   v
Notification Consumer
   |
   v
Email Provider
```

The API may finish before the notification is sent.

Tracing can help you investigate:

* How long message processing takes.

* Whether the consumer received the message.

* How long it waited before processing.

* Whether retries occurred.

* Whether the downstream email provider was slow.

However, a trace must be designed to represent asynchronous boundaries correctly. A delayed consumer operation may occur long after the original request has returned, so its latency should not automatically be interpreted as synchronous API latency.

### 6.5 What is sampling?

At high request volumes, recording every trace may be expensive.

Sampling means retaining only a selected portion of traces.

Common approaches:

* Head sampling: Decide near the beginning of a trace whether to record it.

* Tail sampling: Decide after observing the trace, allowing decisions based on errors, duration, or other attributes.

| Head sampling                      | Tail sampling                                              |
| ---------------------------------- | ---------------------------------------------------------- |
| Low overhead and simpler operation | Can retain important traces based on final outcomes        |
| Decision made early                | Decision made after trace data arrives                     |
| May miss rare failures             | Better at selecting slow or failed traces                  |
| Usually easier to scale            | Requires buffering, routing, and careful capacity planning |

For example, you might retain a baseline percentage of normal traces and a higher percentage of errors or unusually slow traces.

Tail sampling has operational costs: the sampling system needs sufficient buffering, and spans from a trace must reach the appropriate decision-making collector. It also cannot recover spans that were never recorded or were lost before reaching that collector.

Interview question: Should we sample all traces at 100%?

Not always. It depends on traffic, debugging needs, compliance, cost, and system overhead. Low-volume critical workflows may justify full tracing; very high-volume systems often require a carefully designed sampling strategy.

## 7. OpenTelemetry: The modern instrumentation standard

OpenTelemetry, commonly abbreviated as OTel, is an open-source framework for generating, collecting, and exporting telemetry.

It supports metrics, logs, traces, and related observability capabilities. Its key architectural value is that it reduces dependence on a single monitoring vendor.

![](https://www.google.com/s2/favicons?domain=https://opentelemetry.io\&sz=32)

OpenTelemetry

+1

### 7.1 Why does OpenTelemetry exist?

Imagine that every microservice is tightly coupled to a different vendor-specific monitoring SDK.

Changing observability providers could require modifying code across dozens of services.

OpenTelemetry provides common APIs, SDKs, instrumentation libraries, data formats, and conventions so applications can produce telemetry using a more standardized approach.

It is not itself a complete monitoring backend.

### 7.2 OpenTelemetry architecture

Spring Boot / Java Application

Metrics · Logs · Traces

OpenTelemetry API / SDK / Instrumentation

Manual instrumentation and automatic instrumentation

OpenTelemetry Collector

Receive → Process → Export

Metrics Backend

Log Backend

Trace Backend

### 7.3 What does the Collector do?

The OpenTelemetry Collector can:

* Receive telemetry from applications and agents.

* Batch telemetry to improve export efficiency.

* Add or transform attributes.

* Filter unwanted telemetry.

* Apply supported sampling or processing policies.

* Export telemetry to one or more compatible destinations.

A Collector can run as a sidecar, a node-level agent, or a centralized gateway, depending on the deployment.

It can reduce application coupling to backends, but it does not automatically eliminate vendor lock-in: backend query languages, dashboards, retention policies, and proprietary features can still be vendor-specific.

### 7.4 Automatic vs. manual instrumentation

Automatic instrumentation uses supported agents or libraries to collect telemetry for common frameworks and operations.

Examples include supported HTTP server requests, HTTP client calls, and database operations.

Manual instrumentation adds custom spans, metrics, and attributes for business-specific operations.

For example, automatic instrumentation might show that an API request took 500 ms. Manual instrumentation could reveal that the `calculatePremium` business operation consumed 350 ms.

A good architecture often uses both.

### 7.5 What are semantic conventions?

Semantic conventions define common names and meanings for telemetry attributes and operations. This makes telemetry more consistent across teams, libraries, and services.

For example, instead of every team inventing different names for the same HTTP operation, teams can follow standardized OpenTelemetry conventions.

This improves interoperability and reduces confusion in cross-service queries.

## 8. SLIs, SLOs, and SLAs

This topic is essential for senior engineer, architect, and SRE interviews.

### 8.1 SLI — Service Level Indicator

An SLI is a measurement of service performance or reliability.

Examples:

* Percentage of successful requests.

* p95 request latency.

* Percentage of messages processed within 30 seconds.

* Percentage of successful payment operations.

It answers: How well is the service performing?

### 8.2 SLO — Service Level Objective

An SLO is a target for an SLI over a defined measurement window.

Example:

> 99.9% of eligible API requests should succeed over a rolling 30-day window.

Another example:

> 95% of eligible API requests should complete within 300 ms.

An SLO must define what counts as an eligible request, how the measurement is calculated, and the evaluation window.

### 8.3 SLA — Service Level Agreement

An SLA is a formal agreement with customers or other stakeholders about a service commitment, often including consequences when the commitment is missed.

Example:

> The service commits to 99.9% monthly availability, subject to the agreement's definitions and exclusions.

An SLA may have financial or contractual consequences. An SLO is typically an internal reliability target, although organizations may use SLOs in other formal arrangements too.

### 8.4 Quick comparison

| Concept | Meaning            | Example                            |
| ------- | ------------------ | ---------------------------------- |
| SLI     | Actual measurement | 99.92% successful requests         |
| SLO     | Target             | At least 99.9% successful requests |
| SLA     | Formal commitment  | Contractual availability promise   |

### 8.5 What is an error budget?

The error budget is the amount of unreliability permitted by an SLO.

Suppose your SLO is 99.9% successful requests over 30 days.

The error budget is:

100%−99.9%=0.1%100\%-99.9\%=0.1\%100%−99.9%=0.1%

If you receive 10 million eligible requests in the measurement window, the corresponding request-based error budget is:

10,000,000×0.001=10,00010{,}000{,}000 \times 0.001=10{,}00010,000,000×0.001=10,000

That means up to 10,000 requests may fail while the service still meets this request-based target, assuming the SLI definition treats all those failures equally.

Availability measured by time instead of requests would produce a different interpretation. Always define the SLI precisely.

### 8.6 How do error budgets affect deployments?

Imagine your service has almost exhausted its error budget because of repeated outages.

A sensible reliability policy might:

* Pause risky feature releases.

* Prioritize reliability improvements.

* Reduce the blast radius of changes.

* Improve rollback automation.

* Review recent incidents.

If the budget is healthy, the team may accept more controlled experimentation.

Architect's perspective: Error budgets turn reliability into a measurable engineering trade-off rather than a subjective argument between product and operations teams.

## 9. Alerting: Detect problems before customers complain

Dashboards are useful, but someone cannot stare at every dashboard 24 hours a day.

Alerts notify the right people or systems when a condition requires action.

### 9.1 What should you alert on?

Good alerts generally focus on actionable problems, especially symptoms that indicate user impact. The Prometheus project explicitly recommends avoiding unnecessary pages and linking alerts to useful diagnostic context.

![](https://www.google.com/s2/favicons?domain=https://prometheus.io\&sz=32)

Prometheus

+1

Examples:

* Error rate exceeds the agreed threshold.

* API latency violates its SLO.

* Payment success rate drops unexpectedly.

* Queue backlog threatens processing deadlines.

* Database connection exhaustion is causing requests to fail.

* A critical batch job misses its deadline.

* Monitoring data stops arriving unexpectedly.

Avoid creating a high-priority page for every unusual CPU spike if it has no user impact and no immediate action is required.

### 9.2 Threshold-based vs. anomaly-based alerts

Threshold-based alert

Example: alert if database connections remain above 90% of the configured pool for five minutes.

Advantages:

* Easy to explain.

* Predictable.

* Good for known capacity limits.

Disadvantages:

* May miss gradual or unusual patterns.

* Can produce false positives if poorly tuned.

Anomaly-based alert

Example: detect that payment volume is far below its normal level for this hour of the week.

Advantages:

* Can detect unusual behavior without a fixed threshold.

* Useful for seasonal or time-dependent patterns.

Disadvantages:

* Requires sufficient baseline data.

* Can be noisy when patterns change.

* An anomaly does not necessarily mean a failure.

A mature system often combines both approaches.

### 9.3 Alert severity

A simple severity model might be:

| Severity | Meaning                                          | Example                          |
| -------- | ------------------------------------------------ | -------------------------------- |
| Critical | Major customer impact or imminent severe failure | All payments are failing         |
| High     | Significant degradation requiring prompt action  | Error budget burning rapidly     |
| Medium   | Important issue requiring investigation          | Consumer lag steadily increasing |
| Low      | Informational or maintenance issue               | Disk usage trending upward       |

Severity labels should map to clear response expectations, ownership, and escalation policies.

### 9.4 What is alert fatigue?

Alert fatigue happens when engineers receive so many alerts that they begin ignoring them.

Common causes:

* Too many alerts.

* Repeated alerts for the same incident.

* Alerts that require no action.

* Thresholds that are too sensitive.

* Alerts for causes rather than meaningful symptoms.

* No clear ownership.

Solutions:

1. Page only when human action is required urgently.

2. Group duplicate or related alerts.

3. Suppress secondary alerts when a primary incident explains them.

4. Add a runbook link to every operational alert.

5. Use appropriate evaluation windows and hysteresis.

6. Review noisy alerts after incidents.

### 9.5 What is a burn-rate alert?

A burn-rate alert detects how quickly a service consumes its error budget.

If the service is failing much faster than its SLO permits, it may exhaust its budget before the end of the measurement window.

Burn-rate alerting is often more meaningful than an arbitrary error-rate threshold because it connects failures to the service's reliability objective.

### 9.6 Example Prometheus alert

A simplified illustrative rule:

YAML

```
groups:
  - name: application-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          (
            sum(rate(http_server_requests_total{
              status=~"5.."
            }[5m]))
            /
            sum(rate(http_server_requests_total[5m]))
          ) > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "API error rate exceeds 5%"
          description: "Investigate the affected service and its dependencies."
```

This example assumes the metric name and labels exist in your environment. Real rules should handle zero traffic, separate services and routes appropriately, exclude irrelevant requests where justified, and use a carefully defined error SLI.

The `for` clause prevents a brief spike from immediately triggering the alert. Prometheus alerting rules support this pending period and can pass active alerts to Alertmanager for grouping, silencing, inhibition, and notification delivery.

## 11. Java and Spring Boot: Implementing observability

Since you work with Java backend systems, this is an especially useful interview section.

### 11.1 Spring Boot Actuator

Spring Boot Actuator provides production-oriented endpoints and integrations for inspecting and managing application health and metrics.

Common examples include:

* `/actuator/health`

* `/actuator/metrics`

* `/actuator/prometheus` when the appropriate Prometheus registry is configured.

The exact endpoints and available measurements depend on the Spring Boot version and installed dependencies.

Actuator is not a replacement for a complete observability platform. It exposes information that can be collected and analyzed elsewhere.

Security warning: Do not expose sensitive management endpoints publicly. Restrict access, configure endpoint exposure carefully, and apply authentication and network controls where appropriate.

### 11.2 Micrometer

Micrometer is a metrics instrumentation facade commonly used in the Spring ecosystem.

It allows application code to record metrics without tying every measurement directly to a particular metrics backend.

Example:

Java

```
@Service
public class OrderService {

    private final Counter ordersCreated;

    public OrderService(MeterRegistry registry) {
        this.ordersCreated = Counter.builder("orders.created")
                .description("Number of successfully created orders")
                .register(registry);
    }

    public void recordOrderCreated() {
        ordersCreated.increment();
    }
}
```

This simplified example demonstrates a business counter. In a real implementation, increment it at the actual successful order-creation point and ensure that retries or duplicate processing do not accidentally inflate the metric.

### 11.3 Measuring execution time

For custom business operations, use a timer rather than manually calculating averages.

Java

```
@Service
public class PricingService {

    private final Timer pricingTimer;

    public PricingService(MeterRegistry registry) {
        this.pricingTimer = registry.timer("pricing.calculation");
    }

    public Price calculatePrice() {
        return pricingTimer.record(this::doCalculation);
    }

    private Price doCalculation() {
        // Perform the actual pricing calculation.
        return new Price();
    }
}
```

This example assumes a suitable `Price` class exists. In a real application, choose meaningful metric names, units, and tags, and keep high-cardinality values out of metric labels.

### 11.4 Distributed tracing in Spring Boot

A common approach is to use supported OpenTelemetry Java instrumentation or the Spring ecosystem's Micrometer Observation and tracing integrations.

The design should capture:

* Incoming HTTP requests.

* Outgoing HTTP requests.

* Database calls where supported.

* Messaging operations.

* Important business-level operations.

* Errors and relevant span attributes.

For example:

```
POST /orders
    |
    +-- validate-order
    |
    +-- customer-service-call
    |
    +-- payment-service-call
    |
    +-- save-order
```

Instrumentation can generate much of the technical tracing automatically. Add custom spans only where they provide useful additional context.

### 11.5 JVM observability

A healthy API can still suffer from JVM-level performance problems.

Monitor:

| JVM signal                        | What it may reveal                      |
| --------------------------------- | --------------------------------------- |
| Heap occupancy                    | Memory pressure or retained objects     |
| Garbage collection pause duration | Latency caused by GC                    |
| Allocation rate                   | Excessive temporary object creation     |
| Live thread count                 | Thread growth or leaks                  |
| CPU usage                         | CPU-intensive processing                |
| Deadlocked threads                | Potential application hang              |
| Class loading                     | Unusual loading or classloader behavior |
| Direct/native memory              | Memory pressure outside the Java heap   |

For example, suppose your API p99 latency increases from 200 ms to 3 seconds. The database looks healthy, but JVM metrics show long garbage-collection pauses.

That evidence suggests investigating memory allocation, retained objects, heap sizing, and GC behavior rather than immediately scaling the database.

Do not tune garbage collection solely because a graph looks high. Correlate GC behavior with latency, allocation rate, heap occupancy, and workload characteristics.

### 11.6 Database and connection-pool observability

For Spring Boot applications using JDBC or JPA, monitor:

* Connection acquisition latency.

* Active, idle, and pending connections.

* Connection timeout counts.

* Slow queries.

* Lock waits and deadlocks.

* Database CPU and I/O.

* Query execution plans where relevant.

* Transaction duration.

Production scenario: Your API has 1,000 requests per second, and the connection pool has 50 connections. If requests hold connections for too long, the application can accumulate waiting requests even when the database itself is not at full CPU utilization.

The solution is not automatically to increase the pool size. First investigate query duration, transaction boundaries, downstream calls performed while holding connections, database capacity, and connection wait time.

## 12. Observability in Kubernetes and microservices

Kubernetes introduces another layer of moving parts: containers, pods, nodes, deployments, autoscaling, and service networking.

A production strategy must cover both the application and the platform.

### 12.1 What should you monitor in Kubernetes?

| Component          | Important signals                                                   |
| ------------------ | ------------------------------------------------------------------- |
| Pods               | Restarts, readiness, failures, CPU and memory                       |
| Nodes              | CPU pressure, memory pressure, disk space, network                  |
| Deployments        | Desired vs. available replicas, rollout status                      |
| HPA                | Current vs. target metrics, replica count, scaling limits           |
| Ingress / gateway  | Request rate, latency, backend failures                             |
| Cluster networking | DNS errors, connection failures, packet drops where measurable      |
| Persistent volumes | Capacity, latency, mount failures                                   |
| Control plane      | API availability, scheduling and control-plane health where exposed |
| Applications       | RED metrics, logs, traces, business outcomes                        |

### 12.2 Readiness vs. liveness vs. startup probes

This is a frequent Kubernetes interview topic.

* Liveness probe: Is the container still alive? A failed liveness probe may cause Kubernetes to restart it.

* Readiness probe: Is the container ready to receive traffic? A failed readiness probe removes it from normal service endpoints.

* Startup probe: Has a slow-starting application finished starting? It can protect startup from premature liveness failures.

These probes serve different purposes.

A readiness failure should not automatically cause a restart. Likewise, an unhealthy downstream dependency should not necessarily make every instance fail its liveness probe, because repeated restarts can amplify an outage.

### 12.3 Why CPU monitoring alone is not enough

Suppose a Java service has 30% CPU utilization but a high error rate.

Possible causes include:

* Database connection exhaustion.

* External API timeouts.

* Thread-pool starvation.

* Lock contention.

* Queue buildup.

* DNS or network problems.

Low CPU does not prove the service is healthy. A service can be blocked while waiting for external resources.

### 12.4 Detecting cascading failures

Imagine the customer service becomes slow.

1. The order service waits for customer service.

2. Order requests take longer.

3. More requests remain in flight.

4. Threads or connection pools become exhausted.

5. The order service begins timing out.

6. Other services that depend on orders experience failures.

Observability helps identify this chain through latency, traces, in-flight requests, pool utilization, timeouts, and error rates.

Useful resilience controls include:

* Timeouts.

* Bounded queues.

* Bulkheads.

* Circuit breakers.

* Rate limiting.

* Backpressure.

* Retries with limits and jitter.

* Load shedding.

These controls prevent or contain failures. Observability helps verify whether they are working.

## 13. Black-box vs. white-box monitoring

Both approaches are important.

### White-box monitoring

Looks inside the system using internal measurements.

Examples:

* JVM heap metrics.

* Database connection pool usage.

* Internal queue depth.

* Application exceptions.

* Thread-pool utilization.

It helps explain why something is happening.

### Black-box monitoring

Checks the system from the outside, as a user or client would experience it.

Examples:

* Send an HTTP request to the public API.

* Test whether a login journey completes.

* Verify that a synthetic order can be created in a safe test environment.

* Check DNS resolution and TLS connectivity.

It helps establish whether the service is actually usable.

Why do we need both?

Imagine that all internal dashboards show green, but customers cannot access the application because of a broken DNS configuration or load-balancer rule.

An external synthetic check may detect the problem when internal application metrics cannot.

A mature architecture uses internal telemetry to investigate and external checks to validate the customer experience.

## 14. Real User Monitoring and synthetic monitoring

These are related, but they answer different questions.

| Real User Monitoring (RUM)                                | Synthetic monitoring                                       |
| --------------------------------------------------------- | ---------------------------------------------------------- |
| Measures actual user interactions                         | Executes predefined automated checks                       |
| Reveals real-world device and network variability         | Provides repeatable tests                                  |
| Helps analyze user experience across browsers and regions | Helps detect availability and journey failures proactively |
| Depends on actual traffic                                 | Can run even when no customers are active                  |

For a web application, RUM can track page-load time and client-side errors.

Synthetic monitoring might periodically open a login page, submit test credentials in a safe environment, and verify the result.

Architect's decision: Use RUM to understand what users experience and synthetic monitoring to test whether critical journeys remain functional.

Do not use production synthetic tests that create real payments, send real notifications, or modify customer data without safe test identities and controlled side effects.

## 15. Incident response: From alert to root cause

Observability is most valuable when it helps teams act quickly.

Consider a production incident: payment failures increase from 0.2% to 12%.

A structured investigation might look like this:

1. Detect

   Alert on the payment success SLI or error-budget burn rate.

2. Assess impact

   Check the number of failed transactions, affected regions, customer impact, and when the issue began.

3. Correlate signals

   Compare the error-rate and latency metrics with deployment events, logs, traces, and dependency health.

4. Identify the failure domain

   Determine whether the cause is a code deployment, configuration change, database, network, or external payment provider.

5. Mitigate

   Roll back a bad release, disable a faulty feature, route traffic away from an unhealthy dependency, or apply a safe fallback if available.

6. Verify recovery

   Confirm that user-facing metrics return to acceptable levels and that the error rate remains stable.

7. Learn

   Document the incident, conduct a blameless review, and implement preventive actions.

### What is MTTR?

MTTR has several interpretations, including mean time to repair, recover, or resolve. Define which one your organization uses.

Two related metrics are:

* MTTD: Mean time to detect an incident.

* MTTR: Mean time to recover or resolve an incident, depending on the agreed definition.

Improving observability can reduce detection and diagnosis time, but actual recovery also depends on automation, system design, runbooks, and team response.

Do not optimize MTTR by hiding incidents or closing alerts prematurely. Measure customer impact and recovery accurately.

### What is a blameless postmortem?

A blameless postmortem examines why a system allowed an incident to occur and why existing safeguards did not prevent or limit it.

Instead of asking, “Who made the mistake?”, ask:

* What conditions made the failure possible?

* What information was missing?

* Why did testing not catch it?

* Why did the alert not fire earlier?

* Could the blast radius have been reduced?

* What automated safeguard would prevent recurrence?

The goal is to improve the system, not simply assign blame.

## 16. Production scenario: Designing observability for a financial platform

Let's solve a realistic Technical Architect interview question.

Problem statement

You are designing a financial platform built with Java 21, Spring Boot, Oracle, Redis, Google Cloud, and asynchronous messaging through Pub/Sub.

The platform receives thousands of requests per second and must support payment processing, customer notifications, and large batch imports.

How would you design observability?

### Step 1: Define the operational requirements

Before selecting tools, identify what the business needs.

* Detect customer-facing failures quickly.

* Diagnose cross-service latency.

* Detect failed or delayed payments.

* Track message backlog and notification delays.

* Monitor JVM and database capacity.

* Meet availability and latency SLOs.

* Control telemetry costs.

* Protect sensitive financial and customer information.

### Step 2: Instrument every critical component

| Component                 | Required observability                                   |
| ------------------------- | -------------------------------------------------------- |
| API gateway               | Traffic, errors, latency, request IDs                    |
| Spring Boot services      | RED metrics, structured logs, traces                     |
| Oracle                    | Query latency, pool usage, lock waits, database health   |
| Redis                     | Hit ratio, latency, memory, evictions                    |
| Pub/Sub                   | Publish errors, backlog, delivery and processing latency |
| Batch jobs                | Input records, valid/invalid counts, throughput, retries |
| GKE workloads, if used    | Pod health, resource pressure, restarts                  |
| External payment provider | Call latency, timeouts, error rates                      |

### Step 3: Standardize telemetry

Use OpenTelemetry-compatible instrumentation where appropriate, with consistent service names, deployment versions, environment attributes, and trace-context propagation.

Standardization matters because a trace from the order service must connect to the payment service even if different teams own those services.

### Step 4: Define SLIs and SLOs

Illustrative initial targets:

| SLI                              | Example SLO                                                 |
| -------------------------------- | ----------------------------------------------------------- |
| Successful eligible API requests | At least 99.9% over 30 days                                 |
| API latency                      | 95% of eligible requests below 300 ms                       |
| Notification processing          | 99% completed within 60 seconds                             |
| Batch completion                 | All required records processed before the business deadline |

These are example targets, not universal standards. Set them from customer expectations, baseline measurements, business risk, and service dependencies.

For asynchronous processing, define whether “completed” means accepted, delivered, or acknowledged by the final recipient. These are very different business outcomes.

### Step 5: Build actionable dashboards

Create dashboards for:

1. Executive or service-owner health.

2. API and service performance.

3. JVM and thread pools.

4. Oracle and Redis.

5. Pub/Sub and asynchronous processing.

6. Batch job progress and data quality.

7. SLOs and error-budget consumption.

Use shared time ranges and links between metrics, logs, and traces so engineers can move from a symptom to its cause.

### Step 6: Configure alerts

Examples:

* Payment success SLI violates its error-budget policy.

* API latency remains above its SLO.

* Database connection waits are causing request failures.

* Pub/Sub backlog is growing faster than consumers can process it.

* Notification processing deadlines are at risk.

* Batch processing progress is insufficient to meet the deadline.

* Telemetry collection or alert delivery has stopped working.

Assign each alert to an owning team and link it to a runbook.

### Step 7: Protect privacy and manage cost

* Never export payment secrets or authentication tokens.

* Avoid customer IDs, order IDs, and other unique values as metric labels.

* Sample traces appropriately.

* Retain detailed telemetry for a justified period.

* Use aggregation or downsampling for long-term trends where supported.

* Apply access controls and audit access to sensitive logs.

* Monitor the observability pipeline itself.

### Step 8: Test the design

Do not assume observability works simply because dashboards exist.

Run controlled failure tests:

* Make a downstream service slow.

* Exhaust a test connection pool.

* Introduce a failing deployment in a safe environment.

* Simulate consumer backlog.

* Stop telemetry export.

* Verify that alerts reach the right responders.

* Confirm that engineers can identify the affected service from the available evidence.

Architect's conclusion: The design is complete only when the system can detect, explain, and help recover from important failures—not merely produce graphs.

## 17. Common mistakes and anti-patterns

| Mistake                          | Why it is harmful                                             | Better approach                                                |
| -------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------- |
| Monitoring only CPU and memory   | Misses user-facing failures                                   | Track service-level latency, traffic, errors, and saturation   |
| Logging everything at DEBUG      | Increases cost and noise                                      | Use appropriate levels and structured events                   |
| Using averages alone             | Hides tail latency                                            | Track p50, p95, p99 where appropriate                          |
| Alerting on every exception      | Creates alert fatigue                                         | Page on actionable impact; use logs for detailed investigation |
| No trace propagation             | Breaks cross-service visibility                               | Propagate standard trace context                               |
| High-cardinality metrics         | Can explode time-series count and cost                        | Keep unique IDs out of metric labels                           |
| Ignoring failed telemetry export | Creates blind spots                                           | Monitor the collection and export pipeline                     |
| Excessive sampling               | May hide important failures                                   | Design sampling around diagnostic requirements                 |
| No business metrics              | Technical health can look good while business operations fail | Measure completed payments, orders, and processing outcomes    |
| Public management endpoints      | Exposes sensitive operational information                     | Restrict access and apply authentication                       |
| Infinite retries                 | Can amplify outages                                           | Bound retries, use backoff, and enforce deadlines              |
| No runbooks                      | Alerts arrive without a clear response                        | Document investigation and mitigation steps                    |

### What is metric cardinality?

Cardinality is the number of distinct combinations of label values that produce time series.

Suppose you have:

* 10 services.

* 5 HTTP methods.

* 20 routes.

* 5 response-code groups.

A rough upper bound for these combinations is:

10×5×20×5=5,00010 \times 5 \times 20 \times 5 = 5{,}00010×5×20×5=5,000

Now imagine adding a unique `user_id` with one million possible values. The number of possible time series can grow dramatically.

Bad metric label:

```
http_requests_total{user_id="123456"}
```

Better metric labels:

```
http_requests_total{
  service="order-service",
  method="POST",
  route="/orders",
  status_class="2xx"
}
```

The second design groups requests into meaningful categories. Keep unique identifiers in appropriately protected logs or traces when necessary, rather than using them as metric dimensions.

### What is the observability cost problem?

Observability costs can include:

* Telemetry ingestion.

* Storage and retention.

* Query processing.

* Network transfer.

* Collector infrastructure.

* High-cardinality series.

* Trace indexing and search.

* Engineering time to operate the platform.

A good cost-control strategy is not simply “collect less.” First identify which signals support incident response, SLO measurement, security, and compliance. Then use appropriate sampling, aggregation, filtering, retention tiers, and cardinality limits.

### 18.1 OpenTelemetry as a standard instrumentation layer

Many teams use OpenTelemetry to standardize instrumentation across languages, frameworks, and infrastructure.

Why it matters:

* Reduces application coupling to a specific telemetry backend.

* Makes it easier to adopt common semantic conventions.

* Supports a consistent collection pipeline.

* Helps connect telemetry from different services.

OpenTelemetry does not guarantee that every vendor feature becomes portable, but it is a strong foundation for reducing instrumentation fragmentation.

### 18.2 eBPF-based observability

eBPF allows supported programs to run in the operating system kernel under defined safety constraints.

Observability products can use it to collect information about network behavior, system calls, process activity, and other kernel-level events.

Why use it?

It can provide infrastructure or network visibility with less application-code modification than traditional manual instrumentation.

Limitations:

* It does not automatically explain business logic.

* Visibility depends on kernel support, privileges, and the tool.

* Security and operational controls remain important.

* It complements, rather than universally replaces, application-level telemetry.

### 18.3 Continuous profiling

Traditional profiling often happens during a debugging session. Continuous profiling collects performance information over time, allowing engineers to investigate CPU and memory behavior under real workloads.

Useful for:

* Identifying CPU-heavy functions.

* Finding expensive allocations.

* Detecting performance regressions.

* Comparing behavior across deployments.

Profiles answer a different question from traces: traces show where a particular request spent time; profiles help explain where the program spends CPU time or allocates memory.

### 18.4 Observability as code

Instead of configuring everything manually, teams manage dashboards, alert rules, instrumentation settings, and monitoring infrastructure through version-controlled configuration.

Benefits:

* Repeatable environments.

* Peer-reviewed changes.

* Consistent standards across teams.

* Easier recovery and auditing.

* Less configuration drift.

Tools can include Terraform, Helm, Kubernetes manifests, and version-controlled monitoring definitions.

### 18.5 AIOps and AI-assisted incident investigation

AI-assisted operations can help summarize incidents, group related alerts, search telemetry, suggest likely causes, and generate incident timelines.

However, an AI-generated explanation is a hypothesis, not proof.

A responsible architecture should provide:

* Access-controlled telemetry.

* Traceable evidence for proposed causes.

* Human review for high-impact actions.

* Auditable automation.

* Safeguards against sensitive-data leakage.

* Evaluation of false positives and missed incidents.

Do not give an AI agent unrestricted authority to restart services, change production configuration, or modify financial transactions merely because it can analyze monitoring data.

### 18.6 Observability for AI and LLM applications

AI applications introduce new operational questions:

* How long did retrieval take?

* How long did the model call take?

* How many tokens were used?

* What was the cost per request?

* Did the retrieval step return relevant context?

* Did a tool call fail?

* Did the system produce a useful answer?

* Were safety policies followed?

An AI request might be traced as:

```
User Request
    |
    +-- Input Validation
    |
    +-- Embedding Generation
    |
    +-- Vector Database Search
    |
    +-- LLM Request
    |
    +-- Tool Invocation
    |
    +-- Output Validation
    |
    +-- Response
```

You can measure latency, errors, token consumption, and cost while evaluating answer quality with suitable tests.

Critical security point: Prompts, model responses, retrieved documents, and tool arguments may contain sensitive information. Do not automatically record their full contents in production traces. Use redaction, access controls, retention limits, and content capture only where justified.

### 18.7 Business observability

Technical availability does not always equal business success.

For example:

* An API returns HTTP 200, but no order is created.

* A payment request is accepted, but settlement never occurs.

* Messages are consumed, but notifications are not delivered.

* A batch job succeeds technically but processes fewer records than expected.

Modern observability increasingly connects technical signals to business outcomes.

Track events such as:

* Orders successfully completed.

* Payments authorized and settled.

* Duplicate transactions detected.

* Notifications delivered.

* Records imported, rejected, and reconciled.

For financial systems, business telemetry should also support reconciliation and audit requirements without exposing confidential customer data.

1. Is monitoring the same as observability?

No. Monitoring detects known conditions and trends. Observability helps investigate internal system behavior using telemetry. Monitoring is part of an observability strategy.

2. What are the three pillars of observability?

Metrics, logs, and distributed traces. Profiles, events, synthetic checks, and real user monitoring provide additional context.

3. What are the four golden signals?

Latency, traffic, errors, and saturation. Start with these for a user-facing service, then add domain-specific measurements.

4. What is the difference between logs and metrics?

Metrics are numerical measurements over time and are efficient for aggregation and alerting. Logs are individual event records that provide detailed context.

## 20. How to answer architecture interview questions

When an interviewer asks, “Design an observability solution for a microservices platform,” avoid immediately listing tools.

Use this seven-step approach.

1. Understand the business requirements. Identify critical user journeys, availability expectations, security constraints, and recovery objectives.

2. Map the architecture. Identify gateways, services, databases, queues, external dependencies, and deployment infrastructure.

3. Define the SLIs and SLOs. Establish measurable definitions for success, latency, and asynchronous completion.

4. Choose instrumentation. Standardize metrics, structured logs, traces, correlation, and relevant profiling.

5. Design collection and storage. Consider OpenTelemetry, collectors, backends, retention, sampling, cardinality, and regional requirements.

6. Design alerting and response. Set actionable alerts, ownership, escalation, runbooks, dashboards, and safe remediation procedures.

7. Validate operational readiness. Test failure scenarios, telemetry loss, alert delivery, recovery procedures, and cost limits.

A strong senior-level answer explains not only what you would use, but also why you chose it, what trade-offs you accepted, and how you would verify the design.

## The one-minute answer to remember

If an interviewer asks you to summarize Monitoring and Observability, use this:

> Monitoring tells us when our system is unhealthy; observability helps us understand why. I would instrument services with metrics, structured logs, and distributed traces, starting with the four golden signals: latency, traffic, errors, and saturation. I would standardize telemetry using OpenTelemetry where appropriate, define SLIs and SLOs around customer outcomes, and configure actionable alerts tied to error budgets. For a Java microservices platform, I would also monitor JVM behavior, database connection pools, messaging backlogs, and business transaction outcomes. Finally, I would design for secure telemetry collection, controlled cardinality and sampling, cost-effective retention, and tested incident-response procedures.

Remember this principle: Great observability is not about collecting the most data. It is about collecting the right data so the right person can identify and resolve the right problem quickly.
