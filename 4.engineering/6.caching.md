# Caching: The Complete Interview Cheatsheet

*A Medium-style guide for architects. Read it once, remember it forever.*

---

## 1. What is Caching? (The Kid Version)

Imagine you're doing homework and need the value of π again and again. You could walk to the library every time (slow), or write it on a sticky note on your desk (fast).

**That sticky note is a cache.**

> **Caching = storing a copy of expensive-to-get data in a faster, closer place, so the next request is cheap.**

Three words to remember: **Copy, Closer, Faster.**

**Architect's definition:** A cache is a temporary, high-speed storage layer that trades *memory/consistency* for *latency/throughput*. It exploits **locality of reference**: data accessed recently (temporal) or data near accessed data (spatial) is likely to be accessed again.

---

## 2. Why Cache? (The Real Reasons)

| Reason | Explanation |
|---|---|
| **Latency** | RAM access ~100 ns; SSD ~100 µs; network DB call ~1-10 ms. Orders of magnitude difference |
| **Throughput** | Serve more requests with the same hardware |
| **Cost** | Fewer DB reads means smaller DB instances, fewer licenses, less compute |
| **Protect the backend** | Shields DB from traffic spikes (a shock absorber) |
| **Availability** | Can serve stale data when the backend is down (graceful degradation) |
| **Scalability** | Reads scale horizontally via cache; writes are the hard part |

**Interview one-liner:** *"We cache to reduce latency, offload the source of truth, and absorb traffic spikes, at the cost of added complexity and potential staleness."*

---

## 3. When to Cache (and When NOT to)

### ✅ Cache when:
- **Read-heavy** workload (read:write ratio is 10:1 or higher)
- Data is **expensive to compute** (aggregations, reports, ML inference, credit score calculations)
- Data is **expensive to fetch** (cross-region calls, third-party APIs with rate limits)
- Data **changes rarely** (config, product catalog, reference data, user profiles)
- You have **hot spots** (Pareto: 20% of the data gets 80% of the traffic)
- Slight **staleness is acceptable** (view counts, recommendations, feeds)

### ❌ Don't cache when:
- Data is **write-heavy** and changes constantly (cache hit rate will be terrible)
- You need **strong consistency** (bank balance during a transfer, inventory at checkout, seat booking)
- Data is **unique per request** (low or zero reuse means a hit rate near 0%)
- Dataset is **small and the DB is already fast**. Don't add moving parts for nothing
- Data is **highly sensitive** and you can't secure the cache properly (PII, tokens)

> **Golden rule:** *"Don't cache until you've measured. Premature caching creates bugs you can't see."*

## 4. Where to Cache (The Layers)

Think of it as a chain of sticky notes, from closest to the user to closest to the data:

```
User → Browser Cache → CDN → API Gateway/Reverse Proxy → App (In-Memory) → Distributed Cache (Redis) → DB Cache → Disk
```

| Layer | Example | Best for | Typical latency |
|---|---|---|---|
| **Client/Browser** | HTTP cache headers, localStorage, Service Workers | Static assets, API responses per user | 0 ms (no network) |
| **CDN (Edge)** | CloudFront, Cloudflare, Akamai | Images, JS/CSS, videos, static HTML, even cacheable APIs | 5-50 ms |
| **Reverse Proxy / Gateway** | Nginx, Varnish, API Gateway | Full-page or API response caching | ~1-5 ms |
| **Application (Local/In-process)** | Caffeine, Guava, `HashMap`, Ehcache | Ultra-hot, small, read-only data | Nanoseconds to µs |
| **Distributed Cache** | Redis, Memcached, Hazelcast | Shared state across many app instances: sessions, hot entities | ~0.5-2 ms |
| **Database Cache** | Buffer pool, query cache, materialized views | Repeated queries | Built in |
| **OS / Hardware** | Page cache, CPU L1/L2/L3 | Automatic | ns |

### Local vs. Distributed: the classic interview question

| | **Local (In-process)** | **Distributed (Redis)** |
|---|---|---|
| Speed | Fastest (no network) | Network hop (~1 ms) |
| Consistency across nodes | ❌ Each node has its own copy, which can diverge | ✅ Single shared view |
| Memory | Competes with the app heap | Dedicated memory |
| Scaling | Duplicated on every node | Scales independently |
| Failure | Dies with the app | Separate failure domain |
| Best for | Tiny, hot, rarely-changing data | Shared, larger datasets |

**Pro-tip (two-level / L1+L2 cache):** Use a tiny local cache (L1) in front of Redis (L2). It's very fast, but you need invalidation across nodes (e.g., Redis Pub/Sub).

## 5. Core Concepts

### 5.1 Cache Hit, Miss, and Hit Ratio
- **Hit** → data found in cache ✅
- **Miss** → not found, so go to the source ❌
- **Hit Ratio** = hits / (hits + misses)

> A 99% hit ratio vs. 90% is **10× fewer** DB calls (1% vs 10% reach the DB). Small percentage changes at the top have huge backend impact.

**Effective access time** = `(hit% × cache_time) + (miss% × (cache_time + DB_time))`

### 5.2 TTL (Time To Live)
How long an entry lives before it expires. The simplest consistency tool.
- Short TTL → fresher data, lower hit rate
- Long TTL → higher hit rate, staler data
- **Add jitter** (random ±10-20%) so keys don't all expire together (see Avalanche below)

### 5.3 Eviction Policies (What to throw out when full)

| Policy | How it works | Use when |
|---|---|---|
| **LRU** (Least Recently Used) | Evict what hasn't been used for the longest time | General purpose, **the default answer** |
| **LFU** (Least Frequently Used) | Evict what's used least often | Stable hot-set, long-term popularity |
| **FIFO** | Evict oldest inserted | Simple, rarely optimal |
| **TTL-based** | Evict expired first | Time-sensitive data |
| **Random** | Evict a random entry | Cheap, surprisingly OK |
| **W-TinyLFU** | Admission filter plus LRU window (Caffeine) | State of the art for local caches |

**Kid analogy for LRU:** Your toy box is full. You throw out the toy you haven't played with for the longest time.

**Interview gem:** *"LRU is implemented with a HashMap + Doubly Linked List for O(1) get and put."* (Be ready to code it!)

## 6. Caching Strategies (The Most Asked Section!)

### 6.1 Cache-Aside (Lazy Loading) ⭐ *Most common*

```
Read:  App → check cache → HIT? return
                         → MISS? read DB → put in cache → return
Write: App → write DB → invalidate (delete) cache key
```

- ✅ Only caches what's actually requested
- ✅ Cache failure doesn't break the app (falls back to the DB)
- ❌ First request is always slow (cold miss)
- ❌ Possible stale data between the DB write and the invalidation
- **Use:** General purpose, read-heavy

### 6.2 Read-Through
The **cache itself** loads from the DB on a miss (the app only talks to the cache).
- ✅ Simpler app code
- ❌ Cache library/provider must support it
- **Use:** When you want to abstract the DB behind the cache

### 6.3 Write-Through
Write goes to the **cache and DB synchronously**.
- ✅ Cache always consistent with the DB
- ❌ Higher write latency (two writes)
- ❌ Caches data that may never be read
- **Use:** Read-after-write consistency matters

### 6.4 Write-Behind (Write-Back)
Write to the **cache first**, DB updated **asynchronously** later (batched).
- ✅ Very fast writes, DB write batching
- ❌ **Risk of data loss** if the cache crashes before flushing
- ❌ Complex
- **Use:** Write-heavy, loss-tolerant (counters, analytics, likes)

### 6.5 Write-Around
Write goes **directly to the DB**, skipping the cache. The cache is populated only on read.
- ✅ Avoids polluting the cache with write-once data
- ❌ The next read after a write is a miss
- **Use:** Data written once and rarely read (logs, bulk imports)

### 6.6 Refresh-Ahead
Cache **proactively refreshes** hot entries before they expire.
- ✅ Users rarely see miss latency
- ❌ Wasted work if the prediction is wrong
- **Use:** Predictable hot keys (homepage, top products)

### Cheat Table

| Strategy | Read speed | Write speed | Consistency | Data-loss risk | Complexity |
|---|---|---|---|---|---|
| Cache-Aside | Fast after warm | Fast | Eventual | None | Low |
| Read-Through | Fast after warm | Fast | Eventual | None | Medium |
| Write-Through | Fast | Slower | Strong | None | Medium |
| Write-Behind | Fast | **Fastest** | Eventual | **Yes** | High |
| Write-Around | Miss after write | Fast | Eventual | None | Low |
| Refresh-Ahead | **Fastest** | Fast | Near-fresh | None | High |

## 7. Cache Invalidation: "The Hardest Problem"

> *"There are only two hard things in Computer Science: cache invalidation and naming things."* — Phil Karlton

**Why it's hard:** The cache is a *copy*. Whenever the source changes, the copy lies. You must decide *when* and *how* to fix it.

| Approach | How | Trade-off |
|---|---|---|
| **TTL expiry** | Let it expire naturally | Simple, but stale until expiry |
| **Explicit invalidation** | Delete/update the key on write | Accurate, but you must find *every* write path |
| **Event-driven** | DB change → CDC (Debezium) or event bus → invalidate | Decoupled, near real-time, more infra |
| **Versioned keys** | `user:42:v7`, bump the version on change | No deletes needed, old versions age out |
| **Tag-based** | Group keys by tag, invalidate by tag | Flexible, needs support |
| **Write-through** | Update the cache on every write | Always fresh, slower writes |

**Delete vs. Update on write?** Prefer **delete (invalidate)**. Updating the cache risks race conditions where an older write lands after a newer one.

## 8. The Famous Failure Modes (Interview Favorites 🔥)

### 8.1 Cache Penetration
**Problem:** Requests for keys that **don't exist anywhere** (e.g., `user_id=-1`). They always miss and always hit the DB. Often an attack.
**Fixes:**
- **Cache null results** with a short TTL
- **Bloom filter** in front (a quick "definitely not present" check)
- Input validation and rate limiting

### 8.2 Cache Breakdown (Hot Key Expiry / Thundering Herd on one key)
**Problem:** One **very hot key expires**, and thousands of concurrent requests all miss and hit the DB at once.
**Fixes:**
- **Mutex / distributed lock** (only one rebuilds, others wait)
- **Request coalescing / single-flight**
- **Never expire** hot keys, refresh them in the background (logical expiry)
- **Stale-while-revalidate:** serve stale data while one thread refreshes

### 8.3 Cache Avalanche
**Problem:** **Many keys expire at the same time** (or the cache cluster crashes), so the DB is flooded.
**Fixes:**
- **Randomize TTL (jitter)**
- Multi-level caching
- Cache clustering with replication (HA)
- Circuit breakers, rate limiting, graceful degradation
- Warm up the cache before traffic returns

### 8.4 Cache Stampede
Often used interchangeably with breakdown/thundering herd: many requests rebuilding the same value simultaneously. Same fixes (locking, coalescing, probabilistic early expiration).

### 8.5 Hot Key Problem
**Problem:** One key gets a disproportionate share of traffic and overloads a **single Redis shard**.
**Fixes:**
- Local L1 cache for that key
- **Key replication / key sharding** (`key#1..key#N`, random pick)
- Read replicas

### 8.6 Big Key Problem
**Problem:** A huge value (e.g., 50 MB list) blocks Redis (single-threaded commands) and saturates the network.
**Fixes:** Split into smaller keys, compress, use appropriate data structures, avoid `KEYS *` and use `SCAN`.

### 8.7 Stale Data / Inconsistency
A cache and DB disagree. See Section 7. Pick **eventual** vs **strong** consistency deliberately.

### 8.8 Cache Pollution
Rarely-reused data pushes out useful data. Fix with proper eviction, write-around, and admission policies (TinyLFU).

### 8.9 Cold Start
An empty cache after a deploy or restart means a flood of misses. Fix with **cache warming** (pre-load hot data), gradual traffic ramp-up, and persistence (Redis RDB/AOF).

### Quick Memory Table

| Problem | One-line meaning | Top fix |
|---|---|---|
| **Penetration** | Keys that don't exist | Bloom filter / cache nulls |
| **Breakdown** | One hot key expires | Mutex / never-expire + refresh |
| **Avalanche** | Many keys expire together | TTL jitter + HA |
| **Stampede** | Many rebuilding same value | Single-flight / locking |
| **Hot key** | One key overloads a shard | Local cache / key splitting |

## 9. Distributed Caching Deep-Dive

### 9.1 Redis vs. Memcached

| | **Redis** | **Memcached** |
|---|---|---|
| Data types | Strings, Hashes, Lists, Sets, Sorted Sets, Streams, Bitmaps, HyperLogLog, Geo | Strings only |
| Persistence | ✅ RDB/AOF | ❌ |
| Replication / HA | ✅ Replicas, Sentinel, Cluster | ❌ (client-side sharding) |
| Threading | Single-threaded command execution (I/O threads in newer versions) | Multi-threaded |
| Extras | Pub/Sub, Lua scripts, transactions, TTL per key | Simple and lean |
| Best for | Almost everything, feature-rich | Pure simple key-value, multi-core scaling |

**Default answer in interviews: Redis**, unless you only need simple, huge, multi-threaded key-value.

### 9.2 Partitioning (Sharding) the Cache

- **Modulo hashing** (`hash(key) % N`): simple, but adding or removing a node **remaps almost everything** 😱
- **Consistent hashing**: only **~1/N** keys move when nodes change ✅ (with virtual nodes for balance)
- **Redis Cluster**: 16,384 hash slots distributed across nodes

**Kid analogy for consistent hashing:** Kids sit around a circular table. Each toy goes to the next kid clockwise. If one kid leaves, only *their* toys move to the next kid, not everyone's.

### 9.3 Replication and High Availability
- Primary-replica for read scaling and failover
- **Redis Sentinel** → automatic failover
- **Redis Cluster** → sharding plus failover
- Beware **async replication**: failover can lose the latest writes

### 9.4 CAP Theorem & Caches
Distributed caches usually favor **Availability + Partition tolerance (AP)**, accepting eventual consistency.

### 9.5 Persistence in Redis
- **RDB:** periodic snapshots (fast restart, may lose recent data)
- **AOF:** log of every write (safer, larger)
- **Both:** best durability
- **None:** pure cache mode

### 9.6 Redis Eviction Policies (know these names)
`noeviction`, `allkeys-lru`, `allkeys-lfu`, `volatile-lru`, `volatile-lfu`, `volatile-ttl`, `allkeys-random`, `volatile-random`
- `volatile-*` evicts only keys **with a TTL**; `allkeys-*` evicts any key.
- **For a pure cache, use `allkeys-lru` or `allkeys-lfu`.**

## 10. HTTP / Browser / CDN Caching

Important for web-facing architectures.

### Key headers

| Header | Purpose |
|---|---|
| `Cache-Control: max-age=3600` | Cache for 1 hour |
| `Cache-Control: no-cache` | Cache OK, but **revalidate** before use |
| `Cache-Control: no-store` | **Never** store (sensitive data) |
| `Cache-Control: public / private` | Shared caches (CDN) allowed / browser only |
| `s-maxage` | TTL for shared caches (CDN) specifically |
| `ETag` / `If-None-Match` | Validate by content fingerprint, returns `304 Not Modified` |
| `Last-Modified` / `If-Modified-Since` | Validate by timestamp |
| `Vary` | Cache separate versions by header (e.g., `Accept-Encoding`) |
| `stale-while-revalidate` | Serve stale instantly, refresh in the background |
| `stale-if-error` | Serve stale if the origin is down |

**Common gotcha:** `no-cache` ≠ "don't cache." It means "cache, but always revalidate." `no-store` is the "don't cache" one.

### Cache busting (static assets)
Use **content-hashed filenames** (`app.8f3a2c.js`) with `max-age=31536000, immutable`. Deploys change the filename, so no stale assets.

## 11. Database-Level Caching & Related Concepts

- **Buffer pool / page cache:** DB keeps hot pages in memory
- **Query result cache:** the same query returns a cached result (often invalidated broadly, so be careful)
- **Materialized views:** precomputed query results stored as a table
- **Read replicas:** not a cache, but a similar read-scaling goal
- **ORM caches (e.g., Hibernate):** L1 = session, L2 = shared across sessions, plus a query cache. Beware N+1 problems and stale entities.

## 12. Production Scenarios (How You'll Answer "Tell me about a time…")

### Scenario 1: E-commerce product page
- Product details: cache-aside in Redis, TTL 10 min, plus event-driven invalidation on price change
- Images and static assets: CDN
- **Inventory count / checkout: do NOT cache** (or very short TTL and re-verify at checkout)

### Scenario 2: Session store
- Store sessions in Redis with TTL = session timeout
- Enables stateless app servers, so any instance can serve any user

### Scenario 3: Rate limiting
- Redis `INCR` + `EXPIRE` (fixed window), or sorted sets / token bucket via Lua for sliding window
- Atomic, fast, shared across instances

### Scenario 4: Leaderboard
- Redis **Sorted Set** (`ZADD`, `ZREVRANGE`), O(log N), real-time ranking

### Scenario 5: Financial / analytics platform (very relevant to your domain)
- Expensive aggregations (risk scores, portfolio analytics, reports) are cached with a TTL tied to the **data refresh cycle**
- Reference data (currency, country codes, rating scales): long TTL, local cache
- **Per-tenant keys** in SaaS: `tenant:{id}:report:{hash}` → prevents data leakage across customers
- Cache **computed results**, never raw sensitive credentials
- Invalidate when upstream data feeds update (event-driven)

### Scenario 6: API gateway protecting a 3rd-party API
- Cache responses to stay under rate limits and cut per-call costs

### Scenario 7: Flash sale / viral spike
- Pre-warm the cache, use CDN, protect hot keys with a local cache, add request coalescing, and rate-limit origin calls

### Scenario 8: Microservices
- Each service caches its **own** data (avoid shared-cache coupling)
- Use events to invalidate across services
- Beware cascading stale data across service chains

## 13. Best Case vs. Worst Case

### 🟢 Best Case
- **Read-heavy, skewed (hot-set) traffic**, 95-99% hit ratio
- Data rarely changes, so a long TTL is fine
- Cache sized to hold the entire working set
- Result: sub-millisecond responses, DB load drops by 90%+, big cost savings

### 🔴 Worst Case
- **Write-heavy or uniformly random access**, hit ratio near 0%, so you pay for the cache *and* the DB, and latency actually gets worse (extra hop on every miss)
- Cache **down + cold + traffic spike** → avalanche → DB meltdown → full outage
- **Stale data causing business errors** (wrong price, wrong balance, wrong permissions)
- **Security leak** (cache key collisions across users or tenants)
- **Cache stampede** at the worst moment (peak traffic)
- Cache becomes a **hidden single point of failure** that the system can't live without

> **Architect's mindset:** *"The system must remain correct (even if slower) when the cache is empty or down."* The cache is an **optimization, not a dependency for correctness.**

## 15. Design Best Practices Checklist

1. ✅ **Measure first**: profile and find real bottlenecks
2. ✅ Cache **read-heavy, expensive, slow-changing** data
3. ✅ Always set a **TTL** (+ jitter)
4. ✅ Choose the right **strategy** (default: cache-aside)
5. ✅ Use **namespaced, versioned keys**: `service:entity:id:v2`
6. ✅ Protect against **penetration, breakdown, avalanche**
7. ✅ **Monitor**: hit ratio, miss ratio, evictions, latency, memory, key count, hot keys
8. ✅ Design for **cache failure** (fallback, circuit breaker, timeouts)
9. ✅ **Never cache** sensitive data unencrypted or without tenant/user scoping
10. ✅ Size by **working set**, not total data
11. ✅ Compress or serialize efficiently (avoid huge Java-serialized blobs)
12. ✅ Warm critical caches before launch
13. ✅ Document **consistency expectations** per cache

## 16. Java / Spring Quick Reference (Your Home Turf)

### Spring Cache Abstraction
```java
@EnableCaching  // on config class

@Cacheable(value = "users", key = "#id")          // read: check cache, else run method
public User getUser(Long id) { ... }

@CachePut(value = "users", key = "#user.id")      // always run, update cache
public User update(User user) { ... }

@CacheEvict(value = "users", key = "#id")         // remove from cache
public void delete(Long id) { ... }

@CacheEvict(value = "users", allEntries = true)   // clear everything
```

### Gotchas to mention (they impress interviewers)
- `@Cacheable` works via **proxies**, so **self-invocation** (calling a cached method from the same class) **bypasses the cache**
- `null` values: configure `unless = "#result == null"` or cache them deliberately
- Cached objects must be **serializable** (and mind versioning across deploys)
- Use `sync = true` to get single-flight protection against stampedes (per JVM)
- Local libs: **Caffeine** (best), Ehcache, Guava. Distributed: **Redis (Lettuce/Jedis/Redisson)**, Hazelcast

## 18. Monitoring: What to Watch

- **Hit ratio** (target: >90% for most read-heavy caches)
- **Eviction rate** (high means the cache is too small)
- **Latency (p50/p95/p99)**
- **Memory usage and fragmentation**
- **Connection count**
- **Hot keys / big keys**
- **Replication lag**
- **DB QPS** (it should drop after caching)

## 19. FAQ: Interview Questions (With Crisp Answers)

### 🟢 Basics

**Q1. What is caching and why use it?**
Storing frequently accessed data in a faster layer to cut latency, reduce backend load, and improve scalability.

**Q2. Cache hit vs. miss?**
Hit: found in the cache. Miss: not found, so fetch from the source and (usually) populate the cache.

**Q3. What is TTL?**
Time a cache entry stays valid before it expires. It's the simplest consistency control.

**Q4. Name common eviction policies.**
LRU, LFU, FIFO, TTL, Random, and W-TinyLFU.

**Q5. How does LRU work?**
It evicts the least recently used entry. Implemented in O(1) with a HashMap + Doubly Linked List.

**Q6. Redis vs. Memcached?**
Redis: rich data types, persistence, replication, clustering. Memcached: simple, multi-threaded key-value only.

### 🟡 Intermediate

**Q7. Explain cache-aside vs. write-through vs. write-behind.**
Cache-aside: the app manages the cache (lazy load). Write-through: sync write to cache and DB. Write-behind: write to cache, async flush to DB (fast but risks data loss).

**Q8. How do you keep cache and DB consistent?**
You mostly can't make it perfectly strong. Combine TTL, invalidate-on-write (delete, not update), event-driven invalidation via CDC, and versioned keys. Accept eventual consistency, or skip caching for critical data.

**Q9. Why delete the key instead of updating it on write?**
Updating can cause race conditions (an older write overwriting a newer value) and wastes memory on keys that may never be read.

**Q10. Cache penetration vs. breakdown vs. avalanche?**
Penetration: non-existent keys. Breakdown: one hot key expires. Avalanche: many keys expire (or the cache dies) simultaneously.

**Q11. What is a Bloom filter and why use it with a cache?**
A probabilistic structure that says "definitely not present" or "maybe present." It blocks requests for non-existent keys from hitting the DB. False positives are possible; false negatives are not.

**Q12. How do you prevent a thundering herd?**
Mutex/distributed lock, single-flight/request coalescing, stale-while-revalidate, TTL jitter, and background refresh.

**Q13. What is consistent hashing?**
A scheme where nodes and keys are placed on a ring; adding or removing a node only remaps ~1/N of keys. It uses virtual nodes for even distribution.

**Q14. Local vs. distributed cache?**
Local: fastest but per-node and inconsistent. Distributed: shared and consistent but with a network hop. Combine them as L1+L2.

**Q15. How do you cache in a multi-tenant SaaS?**
Tenant-scoped keys (`tenant:{id}:...`), strict authorization checks before reads, and never cache cross-tenant data under a shared key.

### 🔴 Advanced / Architect-Level

**Q16. How do you design a cache for 1M requests/sec?**
CDN and edge caching first, then local L1 (Caffeine) for hot keys, a sharded Redis Cluster with replicas as L2, consistent hashing, hot-key mitigation, TTL jitter, request coalescing, monitoring on hit ratio, and a DB capable of surviving a cold cache.

**Q17. What happens if Redis goes down?**
The app should degrade gracefully: timeouts and circuit breakers, fall back to the DB (with rate limiting to prevent overload), serve stale data if available, and use replicas and failover (Sentinel/Cluster) plus warm-up on recovery.

**Q18. How do you handle the hot key problem?**
Local caching of that key, key replication (`key#1..N` with random reads), read replicas, and client-side caching (Redis tracking).

**Q19. How do you do cache invalidation across microservices?**
Publish domain events (Kafka/SNS) or CDC (Debezium) on data change; each service invalidates its own cache. Keep services decoupled and idempotent.

**Q20. Distributed lock with Redis: is it safe?**
Single-node `SET NX PX` + unique token + Lua release is fine for efficiency locks. For strict correctness, use fencing tokens or consensus-based systems (ZooKeeper/etcd). Redlock is debated for strict safety.

**Q21. How would you size a cache?**
Estimate the working set (hot data, not total data), average value size × key count × overhead (~1.5-2× for Redis metadata), plus headroom. Then validate against the observed hit ratio and eviction rate.

**Q22. What is write-behind's biggest risk?**
Data loss if the cache fails before flushing to the DB. Mitigate with persistence (AOF), a durable queue between the cache and DB, and replication.

**Q23. How do you cache personalized or user-specific data?**
Key by user ID, use shorter TTLs, `private` Cache-Control for browser caching, never `public` on a CDN for user-specific responses, and split into cacheable shared fragments plus small personalized parts.

**Q24. How do you test caching?**
Load tests (cold vs. warm), failure injection (kill Redis), stampede simulations, consistency tests, and hit-ratio monitoring in production.

**Q25. When would you NOT use a cache?**
Strong-consistency needs (financial transactions, inventory at checkout), write-heavy data, unique-per-request data, or when a query-level optimization (an index) is the real fix.

### 🔥 Current Trends (2025-26 Interview Topics)

**Q26. What is semantic caching for LLM applications?**
Instead of exact-match keys, you embed the prompt as a vector and return a cached response if a new prompt is *semantically similar* (above a similarity threshold). It cuts LLM cost and latency. Risks: wrong matches (false hits) and stale answers; tune thresholds and scope by tenant or context.

**Q27. What is prompt caching (LLM providers)?**
LLM APIs can cache a repeated **prompt prefix** (system prompt, documents, tool definitions) so subsequent calls reuse the computed state at lower cost and latency. Design prompts with **stable content first and variable content last** to maximize hits.

**Q28. What is KV cache in LLM inference?**
The attention key/value tensors for already-processed tokens are kept in GPU memory so generation doesn't recompute them for every new token. It's a major memory and throughput factor in model serving.

**Q29. Caching in RAG pipelines?**
Cache embeddings (same text, same vector), retrieval results for frequent queries, and final answers (semantic cache). Invalidate when source documents change.

**Q30. Edge caching and edge compute?**
Cloudflare Workers, Lambda@Edge, and similar run logic at the CDN edge, caching even dynamic or personalized fragments close to users.

**Q31. Client-side caching in Redis?**
Redis can notify clients (tracking/invalidation messages) so apps keep a local cache and still get server-driven invalidation, with fewer network hops.

**Q32. Redis licensing changes: Valkey/alternatives?**
Redis moved to more restrictive licensing in 2024, and the Linux Foundation-backed fork **Valkey** emerged, with major cloud providers supporting it. Alternatives include **Dragonfly** and **KeyDB**. (Verify the current licensing details before quoting them in an interview, since this space keeps changing.)

**Q33. Serverless and caching?**
Functions are stateless and ephemeral, so in-memory caches are lost between cold starts (though warm instances can reuse them). Use external caches (Redis, DynamoDB DAX) and mind connection limits.

**Q34. Cache stampede protection: modern approach?**
**Probabilistic early expiration (XFetch):** each request has a small, increasing probability of refreshing the value *before* it expires, which spreads out the refresh load without locks.

**Q35. Caching in event-driven / CQRS systems?**
Read models (projections) act as purpose-built caches updated from the event stream. Eventual consistency is the accepted cost.

**Q36. How does caching interact with GraphQL?**
Hard to cache at the HTTP level (usually POST, a single endpoint). Use persisted queries, CDN with GET, response caching by operation, and per-field/resolver caches (DataLoader for batching and per-request caching).

**Q37. Observability for caches?**
Use OpenTelemetry metrics and traces. Track hit/miss per key prefix, top hot keys, and the correlation between the hit ratio and backend latency or cost.

## 20. Back-of-the-Envelope Numbers to Remember

| Operation | Approx. time |
|---|---|
| L1 CPU cache | ~1 ns |
| RAM access | ~100 ns |
| Redis GET (same datacenter) | ~0.5-1 ms |
| SSD random read | ~100 µs |
| DB query (indexed, simple) | ~1-10 ms |
| Cross-region network round trip | ~50-150 ms |

A single Redis node can typically handle **~100K ops/sec**; clusters scale far beyond that.

**Rule of thumb:** If the DB takes 20 ms and Redis 1 ms, a 95% hit ratio gives an average of ~`0.95×1 + 0.05×21 ≈ 2 ms`, which is **10× faster** on average.

## 21. How to Structure Your Interview Answer (The Winning Template)

When asked **"How would you add caching to X?"**, answer in this order:

1. **Clarify:** read/write ratio, consistency needs, data size, latency goals
2. **Identify what to cache** and what *not* to
3. **Choose the layer** (CDN / local / distributed)
4. **Choose the strategy** (usually cache-aside) and **eviction + TTL**
5. **Invalidation plan**
6. **Failure modes** (penetration, breakdown, avalanche, hot keys, cache down)
7. **Security/multi-tenancy**
8. **Monitoring and success metrics** (hit ratio, p99 latency, DB load)
9. **Trade-offs:** state clearly what you gave up (consistency, complexity)

> Interviewers love **trade-offs**. Saying "I'd accept eventual consistency here because…" scores more than any tool name.

## 22. Ultra-Short Revision Sheet (Read This 5 Minutes Before the Interview)

- **Cache = fast copy of slow data.** Trades consistency for speed.
- **Where:** Browser → CDN → Gateway → Local → Redis → DB
- **Strategies:** Cache-Aside (default), Read-Through, Write-Through, Write-Behind (fast, risky), Write-Around, Refresh-Ahead
- **Eviction:** LRU (default), LFU, TTL, TinyLFU
- **Always:** TTL + jitter, namespaced keys, monitoring, a fallback if the cache dies
- **Invalidation:** TTL, delete-on-write, events/CDC, versioned keys
- **Failures:** Penetration (Bloom filter/null cache), Breakdown (mutex/refresh), Avalanche (jitter/HA), Hot key (local cache/split)
- **Redis > Memcached** (usually). Consistent hashing for sharding.
- **Don't cache:** strong-consistency data, write-heavy data, unique-per-request data
- **Golden rule:** *The system must stay correct when the cache is empty or down.*
- **Modern:** Semantic cache, prompt caching, KV cache, edge caching, Valkey
