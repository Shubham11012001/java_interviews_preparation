# SAGA, 2PC, and CQRS: The Complete System Design Interview Guide

A Medium-style tutorial for Senior Software Engineers and Technical Architects · Java, Spring Boot, Microservices, and Distributed Systems

Imagine you are designing a banking application. A customer transfers ₹5,000 from Account A to Account B.

What should happen if:

* Account A is debited successfully, but Account B cannot be credited?

* One microservice is down while the others are running?

* Thousands of users are reading account balances while only a few are transferring money?

* A database transaction spans multiple microservices?

* Your application needs to recover after a server crashes halfway through a business operation?

These are not just coding problems. They are distributed systems design problems.

Three important concepts help architects solve different parts of these problems:

SAGA — Manage long-running business transactions

Coordinates multiple services through local transactions and compensating actions.

2PC — Coordinate a distributed commit

Asks all participating resource managers to prepare before committing or aborting a transaction.

CQRS — Separate the read and write models

Optimizes how an application changes data versus how it queries data.

The most important distinction: SAGA and 2PC address transaction coordination. CQRS addresses application and data-model design. They are not competing alternatives, and a single system can use all three.

This guide builds from simple explanations to architecture-level decisions, Java/Spring Boot implementation patterns, failure handling, trade-offs, and modern interview questions.

# 1. Start with the problem: Why do we need these patterns?

## 1.1 What is a distributed transaction?

In a traditional application, multiple database changes can be grouped into one transaction.

SQL

```
BEGIN;

UPDATE accounts
SET balance = balance - 5000
WHERE account_id = 'A';

UPDATE accounts
SET balance = balance + 5000
WHERE account_id = 'B';

COMMIT;
```

Assuming both accounts are in the same transactional database, the database can ensure that both updates commit together or neither does.

This is the familiar ACID transaction model.

* Atomicity: All changes happen, or none happen.

* Consistency: Database constraints and invariants remain valid.

* Isolation: Concurrent transactions are controlled according to the chosen isolation level.

* Durability: Committed changes survive failures within the database's durability guarantees.

Now imagine the transfer involves separate services and databases:

* Account Service → Oracle

* Payment Service → PostgreSQL

* Notification Service → a messaging system

* Loyalty Service → another database

Transfer Request

Account Service

Oracle

Payment Service

PostgreSQL

Notification

Messaging

Loyalty Service

Rewards DB

Different services own different resources. One ordinary local database transaction cannot atomically commit all of them.

Suppose the account debit succeeds, but the payment service fails.

What now?

You need a strategy for coordinating changes across independent resources. This is where distributed transaction patterns become important.

## 1.2 Three questions an architect must answer

| Question                                                              | Relevant concept                                         |
| --------------------------------------------------------------------- | -------------------------------------------------------- |
| How do we coordinate a business transaction across multiple services? | SAGA or, in suitable environments, 2PC                   |
| How do we keep a system correct when a service or message fails?      | Transaction coordination, idempotency, retries, recovery |
| How do we support very different read and write workloads?            | CQRS                                                     |

Keep these questions separate. Many interview answers become weak because candidates describe CQRS as a transaction protocol or assume SAGA provides a global database rollback.

Neither is correct.

# 2. SAGA pattern — Distributed business transactions

## 2.1 What is SAGA?

SAGA is a pattern that breaks a long-running business transaction into a sequence of smaller local transactions, with compensating actions to recover from business failures.

Each service commits its own database transaction. If a later step cannot complete, the system executes compensating actions for earlier completed steps where necessary.

Think of booking a holiday:

1. Reserve a flight.

2. Reserve a hotel.

3. Book a rental car.

If the hotel reservation fails, you may cancel the flight reservation. You do not magically roll back the flight database's committed transaction. You perform a new business operation that releases the reservation.

That is the key idea behind SAGA.

## 2.2 The simplest SAGA diagram

T1: Reserve Flight

Local transaction commits

T2: Reserve Hotel

Local transaction commits

T3: Book Rental Car

Fails

C2: Cancel Hotel Reservation

C1: Release Flight Reservation

T = forward transaction; C = compensating transaction.

The system attempts to restore the relevant business state, but the compensation is not necessarily an exact reversal of every side effect.

For example, if an email has already been sent, you cannot unsend it. You might send a cancellation email instead.

## 2.3 Why do we need SAGA?

SAGA is useful when:

* A business workflow spans multiple microservices.

* Each service owns its own database.

* A global transaction is unavailable, undesirable, or too costly.

* The workflow may take seconds, minutes, or longer.

* Temporary inconsistency is acceptable if the system can recover toward a valid business outcome.

* The system needs explicit recovery logic.

Typical examples include:

* E-commerce checkout.

* Travel booking.

* Loan application processing.

* Order fulfillment.

* Customer onboarding.

* Subscription activation.

* Multi-stage insurance claims.

## 2.4 SAGA in an e-commerce application

Imagine a customer orders a laptop.

The workflow is:

1. Create an order.

2. Reserve inventory.

3. Authorize payment.

4. Arrange shipment.

5. Confirm the order.

Order Service — Create order

Inventory Service — Reserve stock

Payment Service — Authorize payment

Shipping Service — Create shipment

Order Service — Confirm order

Now assume payment authorization fails.

A possible compensation sequence is:

1. Release inventory.

2. Mark the order as payment failed or cancelled.

3. Notify the customer if appropriate.

Notice that we do not necessarily delete the original order record. Keeping the failed order and its history is often valuable for auditing and customer support.

### A subtle but important point

Payment authorization is not the same as capturing money.

An authorization may be voided or released, subject to the payment provider's rules. If money has already been captured, recovery may require a refund, which is a new financial operation and may not be immediate.

An architect must design compensation based on the actual business semantics, not merely reverse database statements.

## 2.5 The two types of SAGA

There are two major implementation styles.

### A. Choreography — Services react to events

There is no central workflow controller. Each service publishes an event, and the next service reacts to it.

Order Service

OrderCreated event

Inventory Service

InventoryReserved event

Payment Service

How it works:

* Order Service commits an order and publishes `OrderCreated`.

* Inventory Service consumes the event, reserves stock, and publishes `InventoryReserved`.

* Payment Service consumes that event and processes payment.

* If payment fails, an event triggers compensation.

Advantages

* Less centralized coordination code.

* Services can remain loosely coupled at runtime.

* Works naturally with event-driven architectures.

* Individual services can evolve independently when event contracts are well designed.

Disadvantages

* The full workflow can be difficult to understand.

* Event dependencies may become circular or overly complex.

* Finding the current workflow state can be difficult without good observability.

* Debugging requires correlating events across services.

* A growing number of services can create a “distributed ball of mud.”

Use choreography when: the workflow is relatively simple, events are natural domain facts, and dependencies remain understandable.

### B. Orchestration — A central coordinator directs the workflow

An orchestrator explicitly knows the next step and the recovery action for each step.

SAGA Orchestrator

Tracks state and chooses the next action

Order Service

Inventory Service

Payment Service

Shipping Service

The orchestrator sends commands and processes replies or events.

Advantages

* Workflow is explicit.

* Compensation logic is easier to locate.

* Easier to implement timeouts, retries, and status tracking.

* Better fit for complex workflows and operational dashboards.

* Makes it easier to reason about which step comes next.

Disadvantages

* The orchestrator becomes an important component that must be made highly available.

* It can become a “god service” if business logic is moved out of the domain services unnecessarily.

* It introduces another stateful component and additional operational complexity.

Use orchestration when: the workflow has many steps, branches, timeouts, compensation rules, or regulatory/audit requirements.

A coordinator is not inherently a single point of failure. Persisted state, recovery after restart, and suitable deployment and failover design can make it resilient.

## 2.6 Choreography vs orchestration

| Factor              | Choreography                  | Orchestration                     |
| ------------------- | ----------------------------- | --------------------------------- |
| Control             | Distributed across services   | Explicit coordinator              |
| Workflow visibility | Emerges from events           | Centralized workflow definition   |
| Simple flows        | Often a good fit              | Can be unnecessary overhead       |
| Complex branching   | Can become difficult          | Usually easier to manage          |
| Failure recovery    | Event reactions               | Explicit compensation workflow    |
| Debugging           | Requires event correlation    | Often easier with workflow state  |
| Coupling risk       | Event dependency complexity   | Coordinator-to-service dependency |
| Best fit            | Simple event-driven processes | Complex business workflows        |

Interview answer: Neither approach is universally better. Choose based on workflow complexity, observability requirements, team boundaries, and failure-recovery needs.

## 2.7 SAGA implementation in Java and Spring Boot

Suppose you are implementing a checkout workflow.

A simplified orchestrator might look like this:

Java

```
public void checkout(Order order) {
    inventory.reserve(order);

    try {
        payment.authorize(order);
    } catch (RuntimeException ex) {
        inventory.release(order);
        throw ex;
    }
}
```

This demonstrates the idea, but it is not production-ready SAGA code.

Why?

* The application can crash after inventory is reserved but before payment is authorized.

* `inventory.release()` can itself fail.

* The payment service may have processed the request even if the client timed out.

* A retry could reserve inventory or authorize payment twice.

* The workflow state is not persisted.

* There is no durable retry or recovery mechanism.

A production design should persist workflow progress and recovery information.

For example:

```
SAGA_ID
ORDER_ID
CURRENT_STEP
SAGA_STATUS
RETRY_COUNT
LAST_ERROR
UPDATED_AT
```

Possible states:

```
STARTED
INVENTORY_RESERVED
PAYMENT_AUTHORIZED
SHIPMENT_CREATED
COMPLETED
COMPENSATING
COMPENSATION_FAILED
CANCELLED
```

Use the exact states your business requires. In particular, `COMPENSATION_FAILED` should not be silently treated as `CANCELLED`.

A robust implementation often combines:

* Spring Boot services.

* Kafka or Google Cloud Pub/Sub for asynchronous communication.

* A durable workflow state store or workflow engine.

* Database transactions local to each service.

* Idempotency keys.

* Transactional outbox and inbox/deduplication patterns.

* Retry policies, dead-letter handling, monitoring, and reconciliation.

The orchestrator can be a custom Spring Boot service or a durable workflow engine, depending on the complexity and reliability requirements.

## 2.8 The Transactional Outbox pattern: A critical SAGA companion

Consider this code:

Java

```
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    kafkaTemplate.send("orders", order);
}
```

There is a dangerous gap.

The database transaction might commit successfully, but publishing the event might fail. Now the order exists, but downstream services never learn about it.

The reverse failure is also possible: the event may be published, but the database transaction later rolls back.

The transactional outbox solves this dual-write problem by storing the business change and an event record in the same local database transaction.

```
Single database transaction
    |
    +-- Save Order
    |
    +-- Save Outbox Event
    |
    +-- COMMIT
             |
             v
     Outbox relay / CDC
             |
             v
      Kafka / Pub/Sub
```

An outbox relay or change-data-capture process publishes the event later.

Important caveats:

* Publishing may happen more than once.

* Consumers should be idempotent.

* Outbox records need cleanup or archival.

* Delivery latency and relay failures must be monitored.

* The outbox does not magically create a transaction spanning the database and the broker.

The outbox pattern is one of the most important reliability patterns to know for modern event-driven microservices.

## 2.9 SAGA failure scenarios an architect must anticipate

| Failure                                     | Correct design response                                                           |
| ------------------------------------------- | --------------------------------------------------------------------------------- |
| Service unavailable                         | Retry with bounded backoff where safe; eventually escalate or compensate          |
| Request times out                           | Treat outcome as potentially unknown; query or reconcile before blindly repeating |
| Duplicate message                           | Deduplicate or make the operation idempotent                                      |
| Event lost before publication               | Use an outbox or another durable delivery mechanism                               |
| Consumer crashes after processing           | Make processing repeat-safe and recoverable                                       |
| Compensation fails                          | Persist the failure, retry, alert, and reconcile                                  |
| Orchestrator restarts                       | Reload durable workflow state and resume safely                                   |
| Message arrives out of order                | Validate workflow state, version, and expected transition                         |
| A customer cancels mid-flow                 | Define which steps are cancellable and which require a separate business action   |
| External payment succeeds but reply is lost | Query provider state using a stable operation/reference ID                        |

### Does SAGA guarantee eventual consistency?

Not by itself.

SAGA supports workflows that can converge toward a valid business outcome if the system has suitable durable state, delivery/retry mechanisms, idempotent operations, and recovery or reconciliation processes.

If a compensation permanently fails, or the system never retries a lost operation, the business state may remain inconsistent.

### Does SAGA provide rollback?

No, not in the database-transaction sense.

A compensation is a new business operation. It may fail, be delayed, or have a different effect from the original operation.

### Is SAGA suitable for financial systems?

Yes, for many cross-service business workflows, but it must be designed carefully.

Financial systems commonly need:

* Immutable transaction records and audit trails.

* Explicit authorization, capture, reversal, and refund semantics.

* Idempotent processing.

* Reconciliation against authoritative payment or ledger systems.

* Strong consistency within the ledger's own transactional boundary.

* Alerts and operational procedures for unresolved discrepancies.

Do not confuse a distributed checkout SAGA with the core atomic posting of a double-entry ledger. The ledger may still require strict local transactional guarantees.

# 3. Two-Phase Commit (2PC) — Distributed atomic transactions

## 3.1 What is 2PC?

Two-Phase Commit is a distributed transaction protocol that coordinates multiple participants so they either all commit a transaction or all abort it, assuming the protocol's required participants and recovery mechanisms operate correctly.

Think of a group of people signing a contract.

The coordinator asks everyone: “Are you ready to sign?”

* If everyone says yes, the coordinator tells everyone to commit.

* If even one participant says no, the coordinator tells everyone to abort.

There are two phases:

1. Prepare phase: Can every participant commit?

2. Commit/abort phase: Tell participants to commit or abort.

The key difference from SAGA is that 2PC coordinates a transactional decision, while SAGA coordinates business operations and compensations.

## 3.2 Why do we need 2PC?

Suppose a financial application updates two independently managed databases:

* Database A records a debit.

* Database B records a credit.

If the system requires both database changes to commit atomically, independently committing each database is insufficient.

2PC can coordinate participating transactional resources that support the necessary protocol. But it introduces coordination overhead and failure-handling complexity.

Important: 2PC does not mean that every arbitrary REST API or microservice can participate in one atomic transaction. The participants must support the relevant transactional protocol and integration.

## 3.3 How 2PC works, step by step

## Phase 1 — Prepare

1. The coordinator asks Participant A and Participant B to prepare.

2. Each participant checks constraints, performs the necessary transactional work, and records enough durable information to commit later.

3. Each participant votes YES or NO.

Coordinator evaluates the votes

Everyone votes YES

Coordinator records the commit decision and instructs participants to commit.

Any participant votes NO

Coordinator instructs participants to abort.

## Phase 2 — Commit or abort

Each participant follows the coordinator's decision and records/completes the outcome.

### A more technical example

Imagine Participant A and Participant B both support the required distributed transaction protocol.

```
Coordinator             Participant A          Participant B
    |                         |                      |
    |------ PREPARE --------->|                      |
    |------ PREPARE ------------------------------->|
    |<----- YES --------------|                      |
    |<----- YES ------------------------------------|
    |                         |                      |
    |---- COMMIT ------------>|                      |
    |---- COMMIT ---------------------------------->|
    |<---- ACK ---------------|                      |
    |<---- ACK -------------------------------------|
```

If one participant votes NO, the coordinator chooses abort instead of commit.

The coordinator must make the global decision durable so it can recover and continue the protocol after a crash.

## 3.4 What happens during the prepare phase?

This is a common interview question.

A participant typically:

1. Executes the work needed to prepare its transaction.

2. Checks whether it can commit.

3. Persists its prepared state and recovery information.

4. Votes YES or NO.

If it votes YES, it is making a serious commitment: it must be able to honor the eventual global decision, including after a restart.

Depending on the database and implementation, the participant may hold locks and other resources while waiting for the final decision.

Why is this important? The participant cannot simply forget the prepared transaction because the coordinator is temporarily unavailable.

## 3.5 What if the coordinator crashes?

This is where 2PC gets interesting.

Suppose both participants vote YES. They enter the prepared state, but the coordinator crashes before delivering the final decision.

The participants may not know whether the global transaction should commit or abort. In standard 2PC, they may need to wait for the coordinator to recover or use an appropriate recovery mechanism.

This creates a potential blocking problem.

The prepared participants may hold locks or other resources, reducing availability while they wait.

2PC can recover when the coordinator and participants recover and their durable logs allow them to complete the protocol. It does not guarantee that progress continues immediately during every network partition or coordinator failure.

## 3.6 Advantages and disadvantages of 2PC

| Advantages                                                        | Disadvantages                                        |
| ----------------------------------------------------------------- | ---------------------------------------------------- |
| Coordinates atomic commit across supported resources              | Can block while waiting for a decision               |
| Participants follow one global commit/abort decision              | Prepared transactions may hold locks                 |
| Useful when atomicity is a hard requirement                       | Adds coordination and network round trips            |
| Supports transactional consistency across resource managers       | Requires compatible transactional infrastructure     |
| Can be suitable for tightly controlled transactional environments | Operational recovery and monitoring are more complex |

## 3.7 When should you use 2PC?

Consider 2PC when:

* You genuinely require atomic commit across participating transactional resources.

* Your infrastructure supports distributed transaction coordination.

* Participants support the necessary protocol.

* The expected availability and latency trade-offs are acceptable.

* The business cannot accept a multi-step compensation model for the relevant operation.

Examples may include coordinated database transactions in legacy enterprise systems, XA-enabled applications, and certain tightly controlled transactional environments.

Do not assume that a microservices architecture automatically benefits from 2PC. Independent services often own their databases and communicate through HTTP or messaging, which generally makes a global ACID transaction impractical.

## 3.8 2PC in Java and Spring

Java enterprise applications can use JTA (Java Transaction API) and XA-capable resources to coordinate distributed transactions.

At a high level:

```
Spring application
       |
       v
JTA transaction manager
       |
       +------ XA-capable Database A
       |
       +------ XA-capable Database B
```

The exact setup depends on the transaction manager, drivers, resource managers, and deployment platform.

A local annotation such as:

Java

```
@Transactional
public void transfer() {
    // update Database A
    // update Database B
}
```

does not automatically guarantee 2PC.

With an ordinary local transaction manager, `@Transactional` usually covers the configured transaction resource or local transaction boundary. To coordinate multiple XA resources, the application needs a suitable distributed transaction configuration and compatible participants.

### Does 2PC require XA?

No, not as an abstract protocol. However, XA is a common standard used to enlist supported resource managers in distributed transactions in Java enterprise systems.

### Does 2PC mean two databases?

No. The two phases are prepare and commit/abort. The number of participants can be greater than two.

### Does 2PC guarantee high availability?

No. It prioritizes a coordinated atomic decision, but the protocol can block under certain failures. High availability depends on the whole system, including recovery, durable logs, networking, and deployment.

### Is 2PC the same as 3PC?

No. Three-Phase Commit introduces an additional phase intended to reduce blocking under specific assumptions. It has its own assumptions and limitations and is not a universal solution to arbitrary network partitions.

# 4. SAGA vs 2PC — The most important comparison

This is one of the questions a Technical Architect should answer confidently.

| Dimension             | SAGA                                                                | 2PC                                               |
| --------------------- | ------------------------------------------------------------------- | ------------------------------------------------- |
| Main goal             | Coordinate a business workflow                                      | Coordinate atomic commit                          |
| Transaction structure | Multiple local transactions                                         | One distributed transaction                       |
| Failure recovery      | Compensating business operations                                    | Commit/abort protocol and recovery                |
| Atomic visibility     | Not globally atomic                                                 | Atomic commit decision under protocol assumptions |
| Locks                 | Usually avoids holding global transaction locks across the workflow | Prepared resources may hold locks                 |
| Availability          | Can often continue with retries and compensation                    | May block during failures                         |
| Consistency model     | Often eventual across services                                      | Atomic commit across enlisted resources           |
| Duration              | Can support long-running workflows                                  | Usually better for shorter transactions           |
| Service independence  | Fits independently owned service databases                          | Requires compatible transactional participants    |
| Business reversals    | Explicit compensating actions                                       | Aborts an uncommitted transaction                 |
| Typical example       | Order, inventory, payment, shipping                                 | Coordinated XA database transaction               |

## 4.1 A simple decision rule

Ask yourself: What must be guaranteed?

“All participating resources must commit atomically, or all must abort.”

Evaluate 2PC if all resources can participate and the availability trade-offs are acceptable.

“The business process spans services, and failures can be handled with retries and compensating actions.”

Evaluate SAGA.

Neither answer is sufficient without clarifying the consistency boundary. For example, an account's balance and ledger entries may need a strongly consistent local transaction even when a larger payment workflow uses SAGA.

## 4.2 Architect-level scenario: A bank transfer

Suppose Account A and Account B belong to the same ledger database.

Recommended starting point: use one local ACID transaction to record the debit and credit, enforcing the ledger's invariants. You may also use appropriate row locking or optimistic concurrency control.

Now suppose the broader operation also involves a payment gateway, fraud checks, customer notifications, and an external settlement process.

The broader workflow may use SAGA or another durable orchestration model, while the core ledger posting remains locally atomic.

This hybrid design is often more sensible than forcing the entire business process into a single distributed transaction.

# 5. CQRS — Command Query Responsibility Segregation

## 5.1 What is CQRS?

CQRS separates the model used to change application state from the model used to read application state.

The full form is Command Query Responsibility Segregation.

Let's make it simple.

A command says:

> “Change something.”

A query says:

> “Tell me something.”

For example, in an e-commerce system:

* `PlaceOrder` is a command.

* `CancelOrder` is a command.

* `GetOrderDetails` is a query.

* `GetCustomerOrderHistory` is a query.

Commands can change state. Queries return information without changing business state.

CQRS separates these responsibilities so each side can be designed and optimized for its own job. This is the core of the pattern described in Microsoft's architecture guidance.

Microsoft Learn

## 5.2 Why do we need CQRS?

Imagine a large online shopping platform.

Every second:

* Thousands of customers browse products.

* Customers search orders and view dashboards.

* A smaller number of customers place or cancel orders.

* Some write operations require complex validation and business rules.

A single data model may struggle to serve all these workloads efficiently, particularly when reads require complicated joins and large aggregations.

CQRS lets you use a write model focused on correct business updates and a read model focused on efficient queries.

## 5.3 Traditional CRUD vs CQRS

### Traditional CRUD

```
Client
  |
  v
Application Service
  |
  v
Single Data Model
  |
  v
Database
```

The same model supports creating, updating, deleting, and reading data.

This is straightforward and is often the right choice for ordinary applications.

### CQRS

```
                 Client
                   |
            +------+------+
            |             |
            v             v
       Command Side   Query Side
            |             |
            v             v
       Write Model    Read Model
            |             |
            v             v
       Write Store    Read Store
```

The write and read sides can share one database or use separate databases.

Important: CQRS does not require microservices, Kafka, separate databases, or event sourcing. Those are optional implementation choices, not the definition of CQRS.

![](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn

## 5.4 Understand commands and queries

| Command                                        | Query                               |
| ---------------------------------------------- | ----------------------------------- |
| Requests a state change                        | Requests information                |
| Usually includes validation and business rules | Usually focuses on retrieving data  |
| Can be accepted or rejected                    | Returns data or a query error       |
| Examples: `PlaceOrder`, `ApproveLoan`          | Examples: `GetOrder`, `SearchLoans` |
| May emit domain events after success           | Should not change business state    |

A command is not just any method that starts with `set`. It represents an intention to perform a business operation.

Similarly, a query is not simply a SQL `SELECT`; it is the application operation whose purpose is to retrieve information.

## 5.5 CQRS does not mean every query needs a separate database

There are two common levels of CQRS.

## Level 1: Logical separation

Command Handler → Write model

Query Handler → Read model

Both models may use the same relational database.

## Level 2: Physical separation

Write Side

Oracle / PostgreSQL

Read Side

Read replica / search index / document store

Separate stores allow independent scaling and query-specific schemas, but require synchronization.

Start with logical separation when it solves the problem. Add physically separate read stores when the workload justifies the operational cost.

## 5.6 CQRS example: Order management

The write model might contain:

```
Order
-----
order_id
customer_id
status
total_amount
version
```

The write side enforces rules such as:

* An order cannot be shipped before it is paid.

* A cancelled order cannot be shipped.

* The order total must be valid.

* Only authorized users can perform certain transitions.

The read model might be a denormalized projection:

```
OrderSummary
------------
order_id
customer_name
product_names
total_amount
payment_status
shipping_status
last_updated_at
```

Why keep these models different?

The write model preserves the business rules and data integrity of the order domain. The read model provides a convenient representation for screens, reports, and APIs.

A customer-order-history page can fetch one prepared projection instead of joining several tables on every request.

## 5.7 CQRS in Java and Spring Boot

A simple design can separate command and query services without any message broker.

Java

```
@Service
public class OrderCommandService {

    private final OrderRepository repository;

    public OrderCommandService(OrderRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public Long placeOrder(PlaceOrderCommand command) {
        Order order = Order.create(command);
        repository.save(order);
        return order.getId();
    }
}
```

And a separate query service:

Java

```
@Service
public class OrderQueryService {

    private final OrderReadRepository readRepository;

    public OrderQueryService(OrderReadRepository readRepository) {
        this.readRepository = readRepository;
    }

    public OrderSummary getOrder(Long orderId) {
        return readRepository.findSummaryById(orderId)
            .orElseThrow(() ->
                new IllegalArgumentException("Order not found"));
    }
}
```

This illustrates separation of responsibilities. The actual `OrderReadRepository` and projection must be implemented for your chosen storage design.

With a shared database, both models may access the same underlying tables. With separate read and write stores, you also need a reliable mechanism to update the read model.

### Is this still CQRS if there is only one database?

Yes. Separate command and query models can share a single data store. Physical database separation is an optional extension.

# 6. CQRS with separate read and write databases

This is where CQRS becomes especially useful in large systems.

## 6.1 Architecture

Imagine the write side uses Oracle and the read side uses a query-optimized PostgreSQL database or search index.

Client / API

Command Handler

Validate and update

Query Handler

Read and return

Write Database

Source of truth

Read Database

Optimized projection

Event / Projection Pipeline

Outbox → messaging or CDC → read-model consumer

The write database remains authoritative for the business state. The read database contains a projection derived from that state.

The read model might be updated asynchronously after the write transaction commits.

## 6.2 What happens when the read model is behind?

Suppose the user places order `123`.

1. The write database commits the order.

2. The API returns success.

3. The event relay publishes the order-created event.

4. The read-model consumer processes it.

5. The read database updates the order summary.

Between steps 2 and 5, a query to the read database may return stale data or report that the new order does not yet exist.

This is eventual consistency.

It is a trade-off, not automatically a bug. The application must decide which operations can tolerate that delay.

### Strategies for handling stale reads

* Return the updated resource or its identifier directly from the write request.

* Route critical read-after-write requests to the authoritative write model.

* Use a projection version or sequence number to detect whether the read model has caught up.

* Allow the client to retry a read when the required version has not yet appeared.

* Display a clear pending state for asynchronous operations.

* Monitor projection lag and define an acceptable service-level objective.

Avoid blindly sending every query to the primary database as a fallback; doing so can overload the very resource CQRS was intended to protect.

## 6.3 Does CQRS guarantee eventual consistency?

No.

CQRS is a separation pattern, not a consistency protocol. If both models share one database and are updated synchronously within a transaction, they may have immediate consistency for the relevant data.

Eventual consistency typically enters the design when the read model is updated asynchronously or maintained in a separate store.

## 6.4 Advantages of CQRS

* Independent optimization of reads and writes.

* Ability to scale read and write workloads separately.

* Simpler, query-specific data representations.

* Separation of business validation from presentation-oriented queries.

* Potentially less contention between read and write workloads.

* Easier integration with search indexes, reporting views, and analytical projections.

## 6.5 Disadvantages of CQRS

* More code and architectural concepts.

* Possible duplication of data.

* Read-model synchronization and event-delivery complexity.

* Eventual-consistency issues when separate stores are used.

* Additional monitoring, deployment, and operational requirements.

* More complicated debugging and testing.

* Schema evolution and replay challenges if event-driven projections are used.

Architect's rule: CQRS is justified when the difference between read and write requirements is significant enough to pay for this complexity.

For a small employee-management CRUD application, a normal Spring Boot service and relational database may be simpler, cheaper, and more reliable.

# 7. CQRS vs Event Sourcing — Do not confuse them

These two patterns are frequently discussed together, but they solve different problems.

## 7.1 What is Event Sourcing?

Event Sourcing stores changes as a sequence of events rather than relying solely on the latest mutable state.

For example, instead of storing only:

```
Account balance = ₹15,000
```

the system might record:

```
AccountOpened       +₹10,000
MoneyDeposited       +₹10,000
MoneyWithdrawn        -₹5,000
```

The current balance is derived from the recorded events, subject to the domain's rules.

In a real financial system, event representation, double-entry accounting, reversals, concurrency, and reconciliation need careful design.

Event Sourcing provides a history of changes and supports rebuilding projections, but it adds substantial complexity around event versioning, replay, and concurrency.

## 7.2 The difference

| CQRS                                 | Event Sourcing                                                  |
| ------------------------------------ | --------------------------------------------------------------- |
| Separates command and query models   | Stores state changes as events                                  |
| Can use ordinary relational tables   | Requires an event store or equivalent append-only event history |
| Does not require an event log        | Requires persisted events as the source of truth                |
| Can be implemented with one database | Can be used with or without CQRS                                |
| Focuses on read/write responsibility | Focuses on how state changes are persisted                      |

A traditional application can use CQRS without Event Sourcing. An event-sourced system can also expose read and write operations through one application interface, although CQRS is a common companion.

## 7.3 When should you combine them?

Consider combining CQRS and Event Sourcing when:

* The domain needs a durable business history.

* Auditing and historical reconstruction are important.

* Many read models need to be built from the same business events.

* Business events are meaningful and useful for downstream consumers.

* The team can operate event storage, replay, schema evolution, and projection infrastructure.

Avoid Event Sourcing merely because the application uses Kafka. Publishing events is not the same as persisting every state-changing event as the authoritative source of truth.

## 8.1 A typical request lifecycle

1. The client sends `PlaceOrder`.

2. The order service validates the request and commits the initial order state.

3. The database transaction records an outbox event.

4. The SAGA orchestrator starts or advances the checkout workflow.

5. Inventory and payment services execute their local transactions.

6. If a step fails, the orchestrator retries or initiates compensation according to policy.

7. Published events update the CQRS read model.

8. The client queries the read model for order details or history.

A robust design must also consider the possibility that the client receives a timeout even though the order was successfully created. A stable idempotency key and an operation-status endpoint can help the client safely discover the outcome.

| ---------------------------------------------------------------------- | ---------------------------------------------- |
| Multiple services must coordinate a business workflow                  | SAGA                                           |
| Earlier business steps must be undone after later failure              | SAGA compensation                              |
| Supported resources must commit one distributed transaction atomically | 2PC                                            |
| Read and write workloads need different models                         | CQRS                                           |
| Database update and event publication must not get out of sync         | Transactional outbox                           |
| A message may be processed more than once                              | Idempotent consumer / deduplication            |

Knowing the definitions is not enough. An interviewer will often ask, “What happens if the system fails at the worst possible moment?”

## 9.2 Observability: What should you measure?

| Component          | Useful metrics                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------- |
| SAGA orchestrator  | Active workflows, completion time, stuck workflows, compensation failures                 |
| Message broker     | Consumer lag, delivery retries, dead-letter volume                                        |
| Outbox relay       | Pending records, oldest unpublished event age, publication failures                       |
| CQRS read model    | Projection lag, update throughput, failed projection events                               |

Do not monitor only CPU and memory. An application can be healthy at the infrastructure level while thousands of business workflows are stuck.

## 9.3 Security and compliance

For enterprise and financial systems:

* Authenticate and authorize commands independently of queries.

* Prevent clients from directly modifying read projections.

* Avoid placing sensitive personal or payment data into events unless necessary and protected.

* Define event retention, access control, and deletion policies.

* Keep audit records for critical business decisions.

* Protect replay and administrative recovery operations.

* Avoid logging credentials, payment secrets, or sensitive payloads.

* Ensure retries cannot bypass business authorization or fraud checks.

Event immutability is not an excuse to retain personal data forever. Data retention and privacy requirements must be part of the architecture.

# 10. FAQ — Common interview questions and strong answers

These are the questions worth practicing aloud for Senior Engineer, Lead Engineer, and Technical Architect interviews.

## SAGA FAQs

### Q1. Is SAGA a replacement for ACID?

No. SAGA coordinates a sequence of local ACID transactions. Each participating service should still preserve the consistency of its own database.

### Q2. Does SAGA guarantee that all services will eventually succeed?

No. It provides a framework for coordinating progress and compensation. Eventual completion depends on durable state, delivery, retries, recovery, and the availability of the required services or manual intervention.

### Q3. Can a SAGA be implemented without Kafka?

Yes. It can use synchronous HTTP, a message broker, a durable workflow engine, or other mechanisms. The essential feature is the sequence of local transactions and recovery actions, not a particular broker.

### Q4. Is choreography always more scalable than orchestration?

No. Both can scale. Choreography avoids a central workflow controller but can make complex dependencies harder to manage. Orchestration adds coordination overhead but can improve workflow visibility and control.

### Q5. What happens if compensation fails?

Persist the failed compensation state, retry when safe, alert operators, and provide a reconciliation or manual-recovery path. Do not mark the workflow as fully compensated if it is not.

### Q6. Can we use SAGA with a relational database?

Yes. A SAGA often uses relational databases for each service's local transactions and workflow state.

### Q7. Should every microservice call be part of a SAGA?

No. Ordinary reads and independent operations do not automatically need SAGA. Use it when multiple business steps must be coordinated and failure recovery requires explicit business semantics.

### Q8. How do you prevent duplicate payments in a SAGA?

Use a stable business-operation or idempotency key, persist processing outcomes, enforce suitable uniqueness constraints, and use the payment provider's idempotency mechanism when available. Handle timeouts by checking the existing operation's status before issuing a new charge.

### Q9. What is the difference between retry and compensation?

A retry attempts the same operation again because it may succeed. Compensation performs a different business operation to counteract a previously completed step.

### Q10. How would you recover a SAGA after a server restart?

Persist workflow state before or atomically with the relevant local progress, then resume from the last durable state. Design transitions so a crash between a side effect and a state update can be detected and safely reconciled.

## 2PC FAQs

### Q11. What are the two phases of 2PC?

Prepare, followed by commit or abort.

### Q12. Why can 2PC block?

After participants prepare, they may need the coordinator's final decision. If the coordinator is unavailable and the decision cannot be determined through recovery, participants may remain in doubt and retain resources.

### Q13. Does 2PC require all participants to vote YES?

Yes, for the coordinator to choose the commit outcome in the normal protocol. A NO vote leads to abort.

### Q14. Does 2PC guarantee that the whole transaction always completes?

No. It coordinates a consistent commit decision, but failures can delay completion and recovery. In particular, it can block during certain coordinator failures.

### Q15. Can 2PC work over REST APIs?

Not automatically. Ordinary REST APIs do not provide prepare/commit semantics. A custom API protocol can implement similar business coordination, but that does not make it a standard transactional 2PC participant.

### Q16. Is 2PC the same as a database transaction?

No. A local transaction typically coordinates one database's transactional resources. 2PC coordinates a distributed transaction across participating resource managers.

### Q17. Does 2PC eliminate the need for idempotency?

No. Application retries, client timeouts, duplicate requests, and other side effects can still require idempotency. 2PC solves a different problem.

### Q18. Why not use 2PC for every microservice workflow?

Because many services do not support a common distributed transaction protocol, and the coordination, blocking, and operational costs may be unacceptable. SAGA is often more suitable for long-running business processes.

## CQRS FAQs

### Q19. Is CQRS the same as CRUD?

No. CRUD describes create, read, update, and delete operations. CQRS explicitly separates the models and responsibilities used for commands and queries.

### Q20. Does CQRS require separate databases?

No. The models can be logically separated while sharing a database. Separate stores are optional.

### Q21. Does CQRS require event-driven architecture?

No. Events are a common way to synchronize separate read and write stores, but basic CQRS can use synchronous calls and one database.

### Q22. Does CQRS automatically improve performance?

No. It can improve performance when read and write workloads have different needs. For a simple CRUD application, it can add unnecessary complexity.

### Q23. How do you maintain consistency between CQRS databases?

Use a reliable update mechanism such as a transactional outbox and idempotent consumers, track projection progress, and define recovery and reconciliation procedures.

### Q24. Can CQRS use Oracle for writes and Elasticsearch for reads?

Yes, if the query requirements justify it. Oracle can remain authoritative while Elasticsearch provides a search-optimized projection. The design must account for indexing delays, failed updates, mapping changes, and reindexing.

### Q25. Can CQRS and Event Sourcing be used independently?

Yes. CQRS separates read/write models. Event Sourcing changes the persistence model by storing state-changing events as the source of truth. They are frequently combined but are distinct patterns.

### Q26. How do you solve read-after-write consistency in CQRS?

Return the write result directly, use the authoritative store for critical reads, or track projection versions and wait until the required version is visible. The right choice depends on the business requirement.

### Q27. How do you rebuild a CQRS read model?

Replay the relevant source events or regenerate the projection from authoritative data, depending on the design. Rebuilds need versioned schemas, checkpointing, duplicate-safe processing, and a controlled cutover strategy.

### Q28. Can CQRS help with security?

Yes. Separate command and query paths can support different permissions and data representations. However, security still depends on correct authorization and data-access controls; CQRS itself is not a security guarantee.

## Five rules to carry into the interview

1. Do not use distributed transactions by default. First identify the smallest boundary that genuinely needs atomic consistency.

2. Do not treat compensation as rollback. Compensation can fail and may not reverse every external side effect.

3. Do not assume events are delivered exactly once. Design for duplicates and recovery.

4. Do not introduce CQRS just to sound scalable. Introduce it when read/write needs justify the added complexity.

5. Do not confuse a successful API response with a fully completed distributed workflow. Make the operation's state and consistency guarantees explicit.

The strongest Technical Architect answer is not “SAGA is better than 2PC” or “CQRS makes applications faster.” It is:

“I will choose the pattern based on the required consistency boundary, the nature of the business operation, failure-recovery requirements, workload characteristics, and the operational complexity the team can support.”

That is the level of reasoning interviewers are looking for.
